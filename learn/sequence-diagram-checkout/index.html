Sequence diagrams: who calls whom, and what happens when a step fails

“A class diagram shows structure; a sequence diagram shows one scenario in time, and its failure branch is where the missing responsibility shows up.”

A sequence diagram lays the participants across the top (one lifeline each) and the messages down the page in the order they happen. Solid arrows are calls, dashed arrows are returns, and a box labelled alt splits the page into the branches of a decision.

Draw one for the main scenario and one for the failure path. The happy path of "place an order" is reserve stock, then charge the card. The failure path asks the question the requirements never did: if the charge is declined, who gives the stock back? On a sequence diagram that is a visible gap, a lifeline with no arrow going to it. In code the fix is a named orchestrator (a use-case or service class) that owns the whole scenario, including its compensating step.

The smell

  • A scenario spread across callers: each caller repeats "reserve, then charge" in its own way.
  • A step that succeeded is never undone when a later step fails (stock stays reserved, a hold stays on the card).
  • You cannot point at the one class that knows the order of the steps.

Before

#include <iostream>

class Inventory {
public:
    bool reserve() {
        if (units_ == 0) return false;
        --units_;
        return true;
    }
    int units() const { return units_; }

private:
    int units_ = 1;
};

class Payment {
public:
    bool charge(int amount) {
        if (amount > funds_) return false;
        funds_ -= amount;
        return true;
    }

private:
    int funds_ = 50;
};

// The scenario lives in a free function; nothing undoes the reservation when the charge fails.
void order(Inventory& inventory, Payment& payment, int amount) {
    if (!inventory.reserve()) {
        std::cout << "sold out\n";
        return;
    }
    if (!payment.charge(amount)) {
        std::cout << "payment declined\n";
        return;
    }
    std::cout << "order placed\n";
}

int main() {
    Inventory inventory;
    Payment payment;
    order(inventory, payment, 80);
    order(inventory, payment, 30);
    std::cout << "units " << inventory.units() << "\n";
}

After

#include <iostream>

class Inventory {
public:
    bool reserve() {
        if (units_ == 0) return false;
        --units_;
        return true;
    }
    void release() { ++units_; }
    int units() const { return units_; }

private:
    int units_ = 1;
};

class Payment {
public:
    bool charge(int amount) {
        if (amount > funds_) return false;
        funds_ -= amount;
        return true;
    }

private:
    int funds_ = 50;
};

// The orchestrator owns the scenario and its compensating step, exactly as the sequence diagram's alt box shows.
class Checkout {
public:
    Checkout(Inventory& inventory, Payment& payment) : inventory_(inventory), payment_(payment) {}

    bool place(int amount) {
        if (!inventory_.reserve()) {
            std::cout << "sold out\n";
            return false;
        }
        if (!payment_.charge(amount)) {
            inventory_.release();  // compensate: give the stock back
            std::cout << "payment declined\n";
            return false;
        }
        std::cout << "order placed\n";
        return true;
    }

private:
    Inventory& inventory_;
    Payment& payment_;
};

int main() {
    Inventory inventory;
    Payment payment;
    Checkout checkout(inventory, payment);
    checkout.place(80);
    checkout.place(30);
    std::cout << "units " << inventory.units() << "\n";
}

What changed, and the trade-off

Same two orders, different outcome. Before: the declined first order leaves the only unit reserved, so the second, perfectly payable order reports "sold out". After: Checkout::place is the single owner of the scenario, and the failure branch calls release(). The class holds its collaborators by reference (aggregation in class-diagram terms), so the diagram and the ownership agree. Trade-off: compensation is best-effort here. If the process dies between reserve and release, the stock is still lost; across services that gap needs a reservation with an expiry or a saga with retries, which is a system-design answer, not a class-design one.

Say it in the interview

Draw the happy path in four arrows, then say "now the failure path: if the charge is declined, who undoes the reservation?" That one question is the Senior signal. Level signal: SDE II gets the main flow right; Senior adds the alt branches and the compensating step; Staff names the partial-failure window and the idempotency or timeout that closes it.

When it goes too far

A sequence diagram for every method is noise; draw one per interesting scenario (usually the main flow and the worst failure). And an orchestrator class for a two-step flow with no failure handling is an extra layer that only forwards calls.
