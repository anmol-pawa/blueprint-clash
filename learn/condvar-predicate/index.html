Condition variables: wait on a predicate, not a notification

“A notification is a hint to re-check the state; the state, under the mutex, is the truth.”

A condition variable lets a thread sleep until some condition over shared state may have changed. The shared state lives under a mutex; wait atomically releases the mutex and sleeps, then reacquires it before returning.

Two facts shape every correct use:

  • A notification is not remembered. If the producer notifies before the consumer starts waiting, that notification is gone. A consumer that waits for "a notify" instead of "the item exists" sleeps forever (a lost wake-up).
  • Wake-ups can be spurious, and another consumer may take the item first. So you always re-check the condition: wait with a predicate (cv.wait(lock, pred)), which is exactly a while (!pred) wait(lock) loop.

The producer changes the state under the mutex, then notifies (before or after unlocking is fine; after is slightly cheaper). Use notify_all when waiters wait for different conditions on the same variable; notify_one is only safe when any one waiter can make progress.

The smell

  • cv.wait(lock) with no predicate, or if (!ready) cv.wait(lock) instead of a loop.
  • The wake-up is treated as proof that the data exists.
  • A flag read outside the mutex that guards it.
  • notify_one with different kinds of waiters on one condition variable.

Before

#include <chrono>
#include <condition_variable>
#include <iostream>
#include <mutex>
#include <optional>
#include <thread>

// The consumer treats "I was notified" as "there is an item". The producer notified earlier, so the item is missed.
class Mailbox {
public:
    void post(int value) {
        {
            std::lock_guard<std::mutex> guard(mutex_);
            value_ = value;
            has_ = true;
        }
        cv_.notify_one();
    }

    std::optional<int> waitFor(std::chrono::milliseconds timeout) {
        std::unique_lock<std::mutex> lock(mutex_);
        const std::cv_status status = cv_.wait_for(lock, timeout);  // BUG: no predicate
        if (status == std::cv_status::no_timeout) return value_;
        return std::nullopt;
    }

private:
    std::mutex mutex_;
    std::condition_variable cv_;
    int value_ = 0;
    bool has_ = false;
};

int main() {
    Mailbox box;
    std::thread producer([&box] { box.post(42); });
    producer.join();  // the post (and its notify) is over before anyone waits
    std::optional<int> got;
    std::thread consumer([&box, &got] { got = box.waitFor(std::chrono::milliseconds(50)); });
    consumer.join();
    std::cout << "consumer saw: " << (got ? std::to_string(*got) : std::string("nothing (item was already posted)")) << "\n";
}

After

#include <chrono>
#include <condition_variable>
#include <iostream>
#include <mutex>
#include <optional>
#include <string>
#include <thread>

// The consumer waits for the state (has_), so a notification that came early cannot be lost.
class Mailbox {
public:
    void post(int value) {
        {
            std::lock_guard<std::mutex> guard(mutex_);
            value_ = value;
            has_ = true;
        }
        cv_.notify_one();
    }

    std::optional<int> waitFor(std::chrono::milliseconds timeout) {
        std::unique_lock<std::mutex> lock(mutex_);
        if (!cv_.wait_for(lock, timeout, [this] { return has_; })) return std::nullopt;
        has_ = false;
        return value_;
    }

private:
    std::mutex mutex_;
    std::condition_variable cv_;
    int value_ = 0;
    bool has_ = false;
};

int main() {
    Mailbox box;
    std::thread producer([&box] { box.post(42); });
    producer.join();
    std::optional<int> got;
    std::thread consumer([&box, &got] { got = box.waitFor(std::chrono::milliseconds(50)); });
    consumer.join();
    std::cout << "consumer saw: " << (got ? std::to_string(*got) : std::string("nothing")) << "\n";
}

What changed, and the trade-off

The predicate overload re-checks has_ under the mutex before sleeping and after every wake-up, which covers the early notification, spurious wake-ups and a rival consumer stealing the item. The consumer also clears has_ while still holding the lock, so the take is atomic with the check.

Trade-offs: a timeout returns an empty optional, which pushes a decision to the caller (retry, give up, alert). A one-slot mailbox is the simplest shape; for many items you want a bounded queue, where you need two conditions (not full, not empty): either two condition variables or notify_all, because a single notify_one can wake the wrong kind of waiter. The Race Hunter "bounded queue" puzzle explores exactly that.

Say it in the interview

Say "the condition variable carries no data; the predicate under the mutex is the truth", and write the predicate overload without being asked. Senior signal: you name lost wake-up and spurious wake-up separately, explain why the flag is set under the mutex, and choose notify_all or two variables for a bounded buffer. Staff signal: you offer a design that avoids the primitive (a blocking queue abstraction) and say what to test with a stress run plus a model checker.

When it goes too far

A condition variable is the wrong tool for a one-shot result (use std::promise/std::future) or a simple "stop" request (use std::stop_token or an atomic flag). Hand-rolled wait loops all over a codebase are a smell; wrap the pattern in one small blocking-queue class and reuse it.
