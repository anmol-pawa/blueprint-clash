12:T48c,In event-driven design a component **publishes a fact** ("order placed") and does not know who cares. Consumers subscribe and react on their own. Adding an email, an analytics counter or an audit trail then means adding a subscriber, not editing the publisher. It is Observer scaled up from one object to a whole module, and the same idea sits behind message brokers in system design.

Three levels are worth telling apart:
- **Synchronous observer:** the publisher calls the listeners in its own call stack. Simple, ordered, but a slow or throwing listener slows or breaks the publisher.
- **Queued event bus:** the publisher enqueues, a dispatcher delivers later. Publisher and consumers are decoupled in time; you now think about ordering, delivery and what happens when a handler fails.
- **Event sourcing:** the events are the stored truth; current state is a fold over the log. You get history, audit and replay, at the price of schema evolution and rebuilding state.

Events name something that **already happened** (`OrderPlaced`), unlike a Command, which asks for something to happen (`PlaceOrder`). Mixing the two up is the most common design error here.13:T7e8,#include <deque>

#include <iostream>
#include <stdexcept>
#include <utility>
#include <vector>

// A fact in the past tense, immutable once published.
struct OrderPlaced {
    int orderId;
};

// A small in-process bus: publish() enqueues, drain() delivers. Handlers cannot break the publisher or each other.
class EventBus {
public:
    using Handler = std::function<void(const OrderPlaced&)>;

    void subscribe(Handler handler) { handlers_.push_back(std::move(handler)); }
    void publish(const OrderPlaced& event) { pending_.push_back(event); }

    void drain() {
        while (!pending_.empty()) {
            const OrderPlaced event = pending_.front();
            pending_.pop_front();
            for (const Handler& handler : handlers_) {
                try {
                    handler(event);
                } catch (const std::exception& error) {
                    std::cout << "handler failed: " << error.what() << "\n";
                }
            }
        }
    }

private:
    std::vector<Handler> handlers_;
    std::deque<OrderPlaced> pending_;
};

// The service knows only the bus. New consumers never touch it.
class OrderService {
public:
    explicit OrderService(EventBus& bus) : bus_(bus) {}
    void placeOrder(int orderId) {
        std::cout << "order " << orderId << " placed\n";
        bus_.publish(OrderPlaced{orderId});
    }

private:
    EventBus& bus_;
};

int main() {
    EventBus bus;
    bus.subscribe([](const OrderPlaced& event) { std::cout << "inventory reserve " << event.orderId << "\n"; });
    bus.subscribe([](const OrderPlaced& event) {
        if (event.orderId == 8) throw std::runtime_error("smtp down");
        std::cout << "email order " << event.orderId << "\n";
    });
    bus.subscribe([](const OrderPlaced& event) { std::cout << "analytics " << event.orderId << "\n"; });

    OrderService service(bus);
    service.placeOrder(7);
    service.placeOrder(8);
    std::cout << "--drain--\n";
    bus.drain();
}
14:T48d,`OrderService` now depends only on the bus and a small event type; inventory, mail and analytics subscribe from outside. Order 8 shows the isolation: the mail handler throws, the failure is reported, and analytics still runs. Publishing returns immediately and delivery happens at `drain()`, so the producer is decoupled in time as well as in code.

**Trade-offs:** you trade explicit control flow for indirection. "What happens when an order is placed?" is no longer answered by reading one method, so name events well and keep a list of subscribers. Ordering is only guaranteed per bus here; across threads or processes you need partitioning, idempotent handlers (delivery is at-least-once in real brokers) and a plan for poison events (retry, dead-letter queue). A handler that subscribes while the bus is dispatching would invalidate the loop, so a production bus snapshots the handler list or forbids it. Event sourcing goes further: you store the events and rebuild state by replaying them, which gives audit and time travel but forces you to version old events forever.
