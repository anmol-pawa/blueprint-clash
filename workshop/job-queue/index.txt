1b:T63c,# Job queue with retries, backoff and a dead-letter queue

You are building the core of an in-process background job queue, the kind behind "send the welcome email", "resize this upload" and "charge the card". Callers enqueue a job, a worker calls its handler, and when the handler fails the queue tries again later, waiting longer each time. A job that keeps failing must not retry for ever: after the last attempt it is parked in a dead-letter queue where a person can look at it. To keep it testable, time is simulated: nothing reads a real clock, and a caller moves time forward with one call.

What you know so far:

- A job has an id and a handler; the handler is called with the attempt number and says whether the work was done.
- A failed job is retried after a delay that grows with every failure.
- A job that runs out of attempts is not lost: it is kept as dead.
- A waiting job can be cancelled, and you can ask where any job is in its life.
- Handlers run on the caller's thread, inside the call that moves time forward.

Your task: design and implement it behind the `jobq::Queue` interface in `api.h`. The hidden tests call only that interface. Ask the interviewer questions first: "how long is the wait after each failure, and measured from when?", "what happens to the job after the last attempt?", "may an id be used again?" and "may a handler enqueue more jobs while it runs?" are where first drafts go wrong. Expect a request for a retry policy per job, and then a request about failures that are not worth retrying and about sending dead jobs back, after you have finished.
1c:T2360,# Editorial: Job queue with retries, backoff and a dead-letter queue

## Requirements
Functional: enqueue a job (id, handler); move simulated time with `advanceTo(t)`, which runs every attempt due; retry a failed attempt after a growing delay; park a job that runs out of attempts in a dead-letter queue; cancel a waiting job; query `state`, `attempts`, `nextAttempt`, `waiting` and `deadLetters`. Then a retry policy per job, and then fatal outcomes, reasons and redrive.

Hidden in the brief and revealed by good questions: the exact running order (time, then first enqueued, never by name, and a retry keeps its job's place); that "due" means at most `t` and that `now()` inside a handler is the attempt's own tick; that the clock never goes backwards; the validation statuses and their order, with ids never reused; that the delay is `10 * 2^(n-1)` ticks after the n-th failure, measured from the failed attempt and not from the target; that the 5th failure kills the job and records it in order of death; that only a Waiting job can be cancelled (`NotFound` versus `NotWaiting`); and that handlers may enqueue and cancel while running, with new work joining the same advance.

**Change Storm 1, a retry policy per job:** `enqueueWith(id, RetryPolicy, handler)` with a maximum number of attempts, a kind of backoff (fixed, linear, exponential), a base delay and a cap on any single delay; a documented check order with `InvalidPolicy` before `DuplicateId`; the policy belongs to that job alone.

**Change Storm 2, failures that are final, and redrive:** handlers return `Done`, `Retry` or `Fatal`; `Fatal` kills the job at once with a reason, exhausted jobs have the other reason; `redrive` sends a dead job back with a fresh attempt count, the same handler and policy, and a new place in line.

## Reference design
`QueueImpl` holds the commands (enqueue, cancel, redrive, advance): it validates, hands out the enqueue rank and delegates, and contains no ordering or retry logic. Its base class `QueueQueries` owns the state and answers every query (`state`, `attempts`, `nextAttempt`, `deadReason`, `waiting`, `deadLetters`, `now`) without changing anything, a small command/query split that also keeps each class to one reason to change. `SimClock` is the only owner of "now". `JobRecord` is one job as a plain value (id, `RetryPlan`, shared handler, state, reason, attempts, due time, rank) and `JobBook` holds every record ever created by id, which is what makes "an id is never reused" and every query a lookup. `RunQueue` keeps an ordered map keyed by (time, rank) and an index by id, and updates both inside `insert`, `remove` and `popDue`, so they cannot disagree; it holds only ids. `DeadLetters` is the list of dead ids in the order they died. `AttemptRunner::runDue` is the loop: pop the next due attempt from the live queue, set the clock to its time, mark the job Running, count the attempt, call the handler, and `settle` the answer. The loop never holds an iterator across user code, so a handler can do anything to the queue.

Storm 1 added `RetryPlan` (how many attempts, which rule, base, cap) and `BackoffRule`, a Strategy with `FixedBackoff`, `LinearBackoff` and `ExponentialBackoff` chosen from a table by the public enum; the cap is applied in one place, the plan. The base design had one hard-coded schedule; the change was a class, a table and one argument, and the runner only asks the plan "exhausted?" and "how long?". Storm 2 changed what a handler may say: the facade wraps a `bool` handler into an `Outcome` handler, and `settle` is the single place that turns an answer into a state (`Done` to Succeeded, `Fatal` to Dead with a reason, `Retry` to Dead when exhausted or to Waiting with a new due time and the same rank). `redrive` is one method that moves a record from Dead to Waiting and puts it in the queue with a new rank. That is the Open/Closed score of the design.

## Alternatives
- **State pattern, one class per state.** `Waiting`, `Running`, `Dead` objects each own the legal operations ("cancel" is legal only in `Waiting`). It reads well at ten states and costs a class per state for five; an enum with the checks in the facade and the transitions in `settle` is easier to see in one screen. Move to the pattern when states grow behaviour of their own.
- **A delay queue as a binary heap.** `std::priority_queue` on (time, rank) is smaller and just as fast for insert and pop, but it cannot remove by id, so cancel marks the entry dead and the pop loop skips it. The ordered map with an id index answers every query exactly.
- **A separate retry queue.** First attempts in one queue and retries in another, merged when due. It makes "the retry keeps its place" a merge rule and doubles the structures to keep consistent; one queue keyed by (time, rank) needs neither.
- **Handlers that throw instead of returning an answer.** The usual C++ shape: an exception means failure, and a special exception type means fatal. It is natural for callers but puts control flow in try/catch inside the loop, and slides into "catch everything". A returned `Outcome` is explicit, testable and cheap; catching exceptions and mapping them to `Retry` is a sensible wrapper on top.
- **Jitter in the delay.** Right for production (it prevents synchronised retry waves) and wrong for tests that need exact ticks; it would be one more `BackoffRule` fed by an injected random source.
- **Deleting finished jobs.** Saves memory and breaks "ids are never reused", so duplicates after success look legitimate. Retention is the real design question.

## Trade-offs
- **Pop before run, Running while it runs.** The queue and the book are consistent whenever user code runs. The cost is that a job that is running cannot be cancelled (`NotWaiting`), which is what the contract documents.
- **Rank on the record.** One counter gives deterministic first come, first served and lets a retry keep its place; a 64-bit counter is enough for ever. A timestamp ties and can go backwards.
- **Shared handler.** The record holds the handler once, so every attempt calls the same callable and its captured state survives; the price is that the handler must not assume a fresh copy per attempt.
- **Plan as data.** The policy is a value looked up per job, not a constant in the loop, so a new rule or limit never touches the loop. The price is one indirection per failure.
- **Strict contract.** Refused calls change nothing, statuses have an order, time cannot go back and ids are never reused. That is what makes the queue something other code can build on.
- **Single thread.** Everything runs on the caller's thread; a slow handler delays the rest and there is no locking. That is the contract of this problem, not the right answer for production.

## What breaks at 10x
- **Records**: keeping every job for ever grows without bound. Expire finished records after a retention period and say what a reused id then means; keep the dead-letter queue until someone handles it.
- **Timers**: millions of waiting jobs make node-per-entry maps heavy. Use a heap in a vector with lazy deletion, or a hierarchical timing wheel with a rule for ordering inside a slot.
- **Synchronised retries**: thousands of jobs failing together retry together. Add jitter and a retry budget, and a circuit breaker so that a down dependency is not hit by every job's schedule.
- **Dead-letter queue**: it grows silently without alerting, a reason and the last error; a bulk redrive must be rate-limited or it recreates the outage.
- **Threads**: a mutex held only around queue and book changes, never around a handler; the guarantee becomes "attempts start in this order", and two attempts of one job must not overlap.
- **Durability**: a restart loses everything. A durable queue keeps rows with a due time, claims them with a lease (a visibility timeout) and runs them at least once, so handlers need an idempotency key.

## Level signals
- **SDE II:** the base problem correct: an ordered structure with an id index, the running order including first come first served, the delay measured from the attempt's own time, the fifth failure ending in the dead-letter queue, ids never reused, and the loop taking the next due attempt from the live queue so a handler can add work. Names the boundary cases (`<=`, an earlier advance, `NotFound` versus `NotWaiting`) before being asked.
- **Senior:** all of the above plus the retry schedule as a per-job Strategy with a capped delay and no change to the loop, an `Outcome` that is settled in one place, a redrive that resets attempts and queue position, and an explanation of why a retry keeps its rank. Raises jitter, poison messages and idempotent handlers unprompted.
- **Staff:** treats the in-memory queue as a model of a durable one: leases and visibility timeouts, at-least-once delivery with idempotency keys, ordering per partition and head-of-line blocking, retry budgets and circuit breakers across the whole queue, and an operating story for the dead-letter queue (alerting, ownership, rate-limited redrive).

// Public API for the Job Queue problem. The hidden tests only use what is declared here.
// You implement jobq::makeQueue() (in any of your .cpp files); everything behind it is your design.
#include <cstddef>
#include <functional>
#include <memory>
#include <string>
#include <vector>

namespace jobq {

enum class Status {
  Ok,
  InvalidId,       // the id is empty or longer than 32 characters
  InvalidHandler,  // the handler is an empty std::function
  InvalidPolicy,   // reserved for per-job retry policies (a later interface); enqueue() never returns it
  DuplicateId,     // the id has been used before, in any state
  NotFound,        // the id has never been used
  NotWaiting,      // the id is known but the job is not Waiting (for cancel and nextAttempt)
  NotDead,         // reserved for the dead-letter queue (a later interface); nothing here returns it
};

enum class State {
  Waiting,    // an attempt (the first one or a retry) is due at nextAttempt()
  Running,    // its handler is being called right now
  Succeeded,  // the handler reported success
  Dead,       // out of attempts; the job sits in the dead-letter queue
  Cancelled,  // removed by cancel() before it could finish
};

// A handler is called once per attempt with the attempt number (1 for the first). It returns true when the work is
// done and false when it failed and may be tried again. Handlers run on the caller's thread, inside advanceTo().
using Handler = std::function<bool(int attempt)>;

constexpr int kMaxAttempts = 5;          // attempts per job: the first one and four retries
constexpr long long kBaseDelay = 10;     // ticks to wait after the first failed attempt
constexpr std::size_t kMaxIdLength = 32;

// A job queue over SIMULATED time: nothing here reads a real clock. Time is a whole number of ticks that starts at 0 and
// moves only when the caller calls advanceTo().
//
// ENQUEUE. enqueue(id, handler) makes a job whose first attempt is due at now(). CHECK ORDER: InvalidId, InvalidHandler,
// DuplicateId. A refused call changes nothing. An id is never reused: it stays taken after the job succeeded, died or was
// cancelled.
//
// ATTEMPTS. advanceTo(t) with t >= now() runs every attempt due at a time <= t, one at a time, earlier time first and
// at the same time the job that was enqueued first (FIFO: a retry keeps the place its job was given when it was
// enqueued), then sets now() to t. While an attempt runs, now() is that attempt's own time and the job is Running. The
// result is the number of attempts that ran. advanceTo(t) with t < now() does nothing and returns 0. A handler may call
// enqueue() and cancel() on this queue (a job it enqueues is due at now() and runs in the same advance); it must not call
// advanceTo().
//
// RETRIES. When an attempt fails and it was not the kMaxAttempts-th, the next attempt is due at (the time of the failed
// attempt) + kBaseDelay * 2^(failed attempts - 1): 10, 20, 40, 80 ticks after attempts 1, 2, 3, 4. The delay is measured
// from the attempt's own time, not from the time advanceTo() was asked to reach. A failure of the kMaxAttempts-th attempt
// makes the job Dead: it leaves the run queue and its id is appended to the dead-letter queue.
//
// CANCEL. cancel(id) turns a Waiting job into Cancelled (it never runs again). NotFound for an unknown id; NotWaiting for
// a known job that is Running, Succeeded, Dead or Cancelled.
class Queue {
 public:
  virtual ~Queue() = default;

  virtual Status enqueue(const std::string& id, Handler handler) = 0;
  virtual Status cancel(const std::string& id) = 0;
  virtual std::size_t advanceTo(long long time) = 0;
  virtual long long now() const = 0;

  // Queries. The out-parameter is touched only on Ok; NotFound for an unknown id.
  virtual Status state(const std::string& id, State& out) const = 0;
  // The number of attempts that have STARTED for the job (the current one counts while it runs).
  virtual Status attempts(const std::string& id, int& out) const = 0;
  // The tick of the next attempt; NotWaiting unless the job is Waiting.
  virtual Status nextAttempt(const std::string& id, long long& at) const = 0;

  // The number of Waiting jobs.
  virtual std::size_t waiting() const = 0;
  // The ids of the Dead jobs, in the order they died (oldest first).
  virtual std::vector<std::string> deadLetters() const = 0;
};

std::unique_ptr<Queue> makeQueue();

}  // namespace jobq

// Change Storm 1: a retry policy per job.
#include "api.h"

namespace jobq {

enum class Backoff { Fixed, Linear, Exponential };

constexpr int kMaxPolicyAttempts = 20;
constexpr long long kMaxBaseDelay = 1000000LL;       // 10^6 ticks
constexpr long long kMaxDelayCap = 1000000000LL;     // 10^9 ticks

// How one job is retried. After the n-th failed attempt (n = 1, 2, ...) the next attempt is due `delay(n)` ticks after
// the failed one, where
//   Fixed        delay(n) = base
//   Linear       delay(n) = base * n
//   Exponential  delay(n) = base * 2^(n - 1)
// and every delay is at most `cap`. The job dies when attempt number `maxAttempts` fails. The default is exactly the
// behaviour of enqueue(): 5 attempts, exponential from 10 ticks (the cap is far beyond what 5 attempts can reach).
struct RetryPolicy {
  int maxAttempts = kMaxAttempts;
  Backoff backoff = Backoff::Exponential;
  long long base = kBaseDelay;
  long long cap = kMaxDelayCap;
};

// makePolicyQueue() has everything makeQueue() has, plus a policy per job.
// enqueueWith(id, policy, handler) CHECK ORDER: InvalidId, InvalidHandler, InvalidPolicy, DuplicateId.
// InvalidPolicy: maxAttempts outside 1..kMaxPolicyAttempts, base outside 1..kMaxBaseDelay, or cap outside
// base..kMaxDelayCap. A policy belongs to that job alone; enqueue() is enqueueWith(id, RetryPolicy{}, handler).
class PolicyQueue : public Queue {
 public:
  virtual Status enqueueWith(const std::string& id, const RetryPolicy& policy, Handler handler) = 0;
};

std::unique_ptr<PolicyQueue> makePolicyQueue();

}  // namespace jobq

// Change Storm 2: failures that are not worth retrying, and sending dead jobs back.
#include "api_storm1.h"

namespace jobq {

// A handler may say more than "it failed":
//   Done   the work is finished (the job Succeeded).
//   Retry  it failed for now: retry under the job's policy (a failure of the last attempt kills the job).
//   Fatal  it can never work (a malformed message, say): the job is Dead at once, whatever attempts are left.
enum class Outcome { Done, Retry, Fatal };
using OutcomeHandler = std::function<Outcome(int attempt)>;

// Why a Dead job is dead.
enum class DeadReason { Exhausted, Fatal };

// makeDrainingQueue() has everything makePolicyQueue() has, plus outcomes, reasons and redrive.
//
// enqueueOutcome(...) has the checks and statuses of enqueueWith(). A plain bool handler behaves as Done / Retry.
//
// deadReason(id, out): Ok for a Dead job; NotFound for an unknown id; NotDead for a job that is not Dead (the out-parameter
// is touched only on Ok).
//
// redrive(id) sends a Dead job back: it becomes Waiting with its first attempt due at now(), its attempt count reset to
// 0 (the handler sees attempt 1 again), the same handler and policy, and a NEW place in the FIFO order (it queues behind
// everything already enqueued). It leaves the dead-letter queue at once. NotFound for an unknown id; NotDead otherwise.
class DrainingQueue : public PolicyQueue {
 public:
  virtual Status enqueueOutcome(const std::string& id, const RetryPolicy& policy, OutcomeHandler handler) = 0;
  virtual Status deadReason(const std::string& id, DeadReason& out) const = 0;
  virtual Status redrive(const std::string& id) = 0;
};

std::unique_ptr<DrainingQueue> makeDrainingQueue();

}  // namespace jobq

// Runs what is due. Each attempt leaves the run queue before its handler is called and the job is marked Running, so a
// handler can enqueue or cancel anything while it runs. What the handler answers decides what happens to the job.
class AttemptRunner {
 public:
  AttemptRunner(JobBook& book, RunQueue& queue, DeadLetters& dead, SimClock& clock)
      : book_(book), queue_(queue), dead_(dead), clock_(clock) {}

  std::size_t runDue(long long target) {
    std::size_t ran = 0;
    std::string id;
    long long at = 0;
    while (queue_.popDue(target, id, at)) {
      clock_.set(at);
      attempt(*book_.find(id));
      ++ran;
    }
    clock_.set(target);
    return ran;
  }

 private:
  void attempt(JobRecord& job) {
    job.state = jobq::State::Running;
    const int number = ++job.attempts;
    const auto handler = job.handler;
    settle(job, (*handler)(number));
  }

  void settle(JobRecord& job, jobq::Outcome outcome) {
    if (outcome == jobq::Outcome::Done) {
      job.state = jobq::State::Succeeded;
    } else if (outcome == jobq::Outcome::Fatal) {
      bury(job, jobq::DeadReason::Fatal);
    } else if (job.plan.exhausted(job.attempts)) {
      bury(job, jobq::DeadReason::Exhausted);
    } else {
      job.state = jobq::State::Waiting;
      job.at = clock_.now() + job.plan.delayAfter(job.attempts);
      queue_.insert(job.id, job.at, job.rank);
    }
  }

  void bury(JobRecord& job, jobq::DeadReason reason) {
    job.state = jobq::State::Dead;
    job.reason = reason;
    dead_.add(job.id);
  }

  JobBook& book_;
  RunQueue& queue_;
  DeadLetters& dead_;
  SimClock& clock_;
};

// How long to wait after the n-th failed attempt (Strategy). The caller applies the cap.
class BackoffRule {
 public:
  virtual ~BackoffRule() = default;
  virtual long long delayAfter(int failedAttempts, long long base) const = 0;
};

class FixedBackoff : public BackoffRule {
 public:
  long long delayAfter(int, long long base) const override { return base; }
};

class LinearBackoff : public BackoffRule {
 public:
  long long delayAfter(int failedAttempts, long long base) const override { return base * failedAttempts; }
};

class ExponentialBackoff : public BackoffRule {
 public:
  long long delayAfter(int failedAttempts, long long base) const override { return base * (1LL << (failedAttempts - 1)); }
};

inline std::shared_ptr<const BackoffRule> makeRule(jobq::Backoff which) {
  static const std::array<std::shared_ptr<const BackoffRule>, 3> table = {
      std::make_shared<FixedBackoff>(), std::make_shared<LinearBackoff>(), std::make_shared<ExponentialBackoff>()};
  return table[static_cast<std::size_t>(which)];
}

    if (!handler) return checked(id, policy, nullptr);
    auto outcome = [h = std::move(handler)](int attempt) { return h(attempt) ? jobq::Outcome::Done : jobq::Outcome::Retry; };
    return checked(id, policy, std::move(outcome));
  }

    return checked(id, policy, std::move(handler));

    JobRecord* job = book_.find(id);
    if (!job) return jobq::Status::NotFound;
    if (job->state != jobq::State::Waiting) return jobq::Status::NotWaiting;
    queue_.remove(id);
    job->state = jobq::State::Cancelled;
    return jobq::Status::Ok;
  }

    JobRecord* job = book_.find(id);
    if (!job) return jobq::Status::NotFound;
    if (job->state != jobq::State::Dead) return jobq::Status::NotDead;

    job->state = jobq::State::Waiting;
    job->attempts = 0;
    job->at = clock_.now();
    job->rank = nextRank_++;
    queue_.insert(id, job->at, job->rank);
    return jobq::Status::Ok;

 private:
