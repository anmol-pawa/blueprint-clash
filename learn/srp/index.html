Single Responsibility: one reason to change

“A class should answer to one actor: if two different teams can force edits to it, split it.”

SRP is about axes of change, not method counts. Ask: who would ask me to edit this class? If finance, the reporting team and the storage team all do, three unrelated reasons share one file, and each team can break the others.

Cohesion is the practical test: do the fields and methods change together? If half the fields are used by half the methods, you probably have two classes wearing one coat.

The smell

  • A class name ending in Manager, Helper or Processor that does calculation, formatting and I/O.
  • Methods that touch disjoint subsets of the fields.
  • A change to the report layout forces a retest of the tax maths.
  • Unit tests need a database or a console just to check an arithmetic rule.

Before

#include <iostream>
#include <string>
#include <vector>

// One class, three reasons to change: pricing rules, text layout, and where output goes.
class Invoice {
public:
    void addLine(const std::string& name, int cents) { names_.push_back(name); cents_.push_back(cents); }
    int totalCents() const {
        int sum = 0;
        for (int c : cents_) sum += c;
        return sum + sum / 10;  // 10% tax baked in
    }
    void print() const {
        for (size_t i = 0; i < names_.size(); ++i) std::cout << names_[i] << ": " << cents_[i] << "\n";
        std::cout << "total: " << totalCents() << "\n";  // layout and destination fixed here
    }
private:
    std::vector<std::string> names_;
    std::vector<int> cents_;
};

int main() {
    Invoice inv;
    inv.addLine("pen", 200);
    inv.addLine("book", 1000);
    inv.print();
}

After

#include <iostream>
#include <sstream>
#include <string>
#include <utility>
#include <vector>

struct Line {
    std::string name;
    int cents;
};

// Reason to change 1: the pricing rules.
class Invoice {
public:
    void addLine(std::string name, int cents) { lines_.push_back({std::move(name), cents}); }
    int totalCents() const {
        int sum = 0;
        for (const Line& l : lines_) sum += l.cents;
        return sum + sum / 10;
    }
    const std::vector<Line>& lines() const { return lines_; }
private:
    std::vector<Line> lines_;
};

// Reason to change 2: the text layout. Pure function of the invoice, no I/O.
class InvoiceFormatter {
public:
    std::string format(const Invoice& inv) const {
        std::ostringstream out;
        for (const Line& l : inv.lines()) out << l.name << ": " << l.cents << "\n";
        out << "total: " << inv.totalCents() << "\n";
        return out.str();
    }
};

// Reason to change 3: where the text goes. The caller chooses; tests can pass a stringstream.
void write(std::ostream& os, const std::string& text) { os << text; }

int main() {
    Invoice inv;
    inv.addLine("pen", 200);
    inv.addLine("book", 1000);
    write(std::cout, InvoiceFormatter().format(inv));
}

What changed, and the trade-off

The arithmetic, the layout and the destination now change independently. The tax rule is testable with no stream at all, and a JSON formatter is a new class instead of an edit to Invoice.

Trade-off: three small types are more to navigate than one. For a 40-line script that never grows, the original is fine. Split when you can name two different people who would ask for edits.

Say it in the interview

Say the actor out loud: "this class changes when finance changes tax, and when design changes the receipt, so I'll separate them". Interviewers at SDE II look for you naming the reason to change, not reciting the acronym. At Senior and above, also say what you did not split and why.

When it goes too far

Splitting by method count produces dozens of one-method classes that all have to be wired together, which spreads one change across many files (shotgun surgery) and makes the flow hard to read. If two pieces always change together, they are one responsibility; keep them together.
