Mediator: one place where the colleagues meet

“Make peers talk to a coordinator instead of to each other, so the coupling is one-to-one instead of everyone-to-everyone.”

A Mediator is a coordinator that peers talk through. Without one, each of N objects holds references to the others it interacts with, which can grow toward N x (N-1) links: change one peer and you touch the rest. With one, each peer knows only the mediator, and the rules about who reacts to whom live in a single class.

Use it when a group of objects has rich, interdependent rules (a lobby, a chat room, an air-traffic tower, form fields that enable and disable each other). The peers become simple and reusable because they carry no knowledge of the others.

In C++ be explicit about lifetime. A peer that stores a reference to the mediator needs the mediator to outlive it, and a mediator that stores raw pointers to peers needs a way to hear that a peer is gone. Storing identifiers (names or ids) instead of pointers sidesteps most of that. And watch the failure mode: a mediator that absorbs every rule becomes a god object.

The smell

  • Every object keeps a list of pointers to its peers, and each wires up all the others.
  • Adding a new participant means editing every existing one.
  • A rule about the whole group (everyone is ready) is checked in each member and is slightly different in each.
  • Peers cannot be reused or tested without the full set around them.

Before

#include <iostream>
#include <string>
#include <utility>
#include <vector>

// Each player knows every other player, and each one re-checks the group rule.
class Player {
public:
    explicit Player(std::string name) : name_(std::move(name)) {}
    void addPeer(const Player* peer) { peers_.push_back(peer); }
    bool isReady() const { return ready_; }

    void ready() {
        ready_ = true;
        std::cout << name_ << " ready\n";
        for (const Player* peer : peers_) {
            if (!peer->isReady()) return;
        }
        std::cout << name_ << " starts the match\n";
    }

private:
    std::string name_;
    bool ready_ = false;
    std::vector<const Player*> peers_;
};

int main() {
    Player a("ann"), b("ben"), c("cy");
    a.addPeer(&b); a.addPeer(&c);
    b.addPeer(&a); b.addPeer(&c);
    c.addPeer(&a); c.addPeer(&b);
    a.ready();
    b.ready();
    c.ready();
}

After

#include <iostream>
#include <map>
#include <string>
#include <utility>

// The mediator owns the group rule. It stores names, not pointers, so a peer cannot dangle in it.
class Lobby {
public:
    void join(const std::string& name) { ready_[name] = false; }

    void markReady(const std::string& name) {
        ready_[name] = true;
        std::cout << name << " ready\n";
        for (const auto& entry : ready_) {
            if (!entry.second) return;
        }
        std::cout << name << " starts the match\n";
    }

private:
    std::map<std::string, bool> ready_;
};

// A player knows only the lobby (which must outlive it).
class Player {
public:
    Player(std::string name, Lobby& lobby) : name_(std::move(name)), lobby_(lobby) { lobby_.join(name_); }
    void ready() { lobby_.markReady(name_); }

private:
    std::string name_;
    Lobby& lobby_;
};

int main() {
    Lobby lobby;
    Player a("ann", lobby);
    Player b("ben", lobby);
    Player c("cy", lobby);
    a.ready();
    b.ready();
    c.ready();
}

What changed, and the trade-off

Behaviour is identical. The "everyone is ready" rule now exists once, in Lobby; a fourth player is one more Player and no edit to the other three (before, it meant six extra addPeer calls and a risk of forgetting one). Player is trivial and can be tested with a stub lobby. The lobby stores names rather than pointers, so a destroyed player cannot leave a dangling entry (a real lobby would also offer leave).

Trade-offs: the coupling has moved, not vanished: the mediator knows every colleague's protocol and can grow into a god object, so keep rules for *one* interaction group in it and split by group. It is also a single point to test and a potential bottleneck. If peers only broadcast "something happened" with no rules, an Observer or an event bus is lighter. Compare with Facade: a Facade simplifies access *to* a subsystem one-way, a Mediator coordinates two-way traffic *among* peers.

Say it in the interview

Say "these objects have many interdependent interactions, so I'll route them through one coordinator". Draw N boxes with N^2 lines, then N lines to a hub. Senior signal: you name the god-object risk and how to split it, state lifetimes (reference to the mediator, names instead of pointers), and distinguish Mediator from Observer (rules and two-way versus broadcast) and from Facade (one-way simplification). Typical uses: chat rooms, elevator controllers, auction houses and UI form logic.

When it goes too far

Two objects that interact in one simple way do not need a go-between. A mediator that every class in the system funnels through becomes the new tangle, with all the rules in one file and a reason for every change to touch it. If the colleagues are already coupled through a clean interface, adding a mediator just adds a hop.
