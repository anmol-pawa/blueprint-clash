Dependency Inversion: depend on abstractions you own

“High-level policy should not construct or know low-level details; both depend on an interface the policy owns.”

When OrderService creates its own SmtpMailer, you cannot test the service without a mail server, and you cannot change the transport without editing the service. Invert it: the service declares the interface it needs (Notifier), and the concrete detail is handed in, typically through the constructor.

Dependency injection is the mechanism; dependency inversion is the design rule that the abstraction belongs to the high-level module.

The smell

  • new or a concrete member of an I/O class inside business logic.
  • Business logic that includes a driver or client header.
  • Tests that need the network, a clock or the file system.
  • A singleton reached from deep inside a method.

Before

#include <iostream>
#include <string>

class ConsoleMailer {
public:
    void send(const std::string& msg) const { std::cout << "mail: " << msg << "\n"; }
};

// Welded to ConsoleMailer: cannot test without printing, cannot swap the transport.
class OrderService {
public:
    void place(const std::string& item) const { mailer_.send("ordered " + item); }
private:
    ConsoleMailer mailer_;
};

int main() {
    OrderService svc;
    svc.place("pen");
}

After

#include <iostream>
#include <memory>
#include <string>
#include <utility>
#include <vector>

// Owned by the high-level module: expressed in its own vocabulary.
class Notifier {
public:
    virtual ~Notifier() = default;
    virtual void notify(const std::string& msg) = 0;
};

class ConsoleNotifier : public Notifier {
public:
    void notify(const std::string& msg) override { std::cout << "mail: " << msg << "\n"; }
};

// A test double: records instead of sending.
class RecordingNotifier : public Notifier {
public:
    void notify(const std::string& msg) override { sent_.push_back(msg); }
    const std::vector<std::string>& sent() const { return sent_; }
private:
    std::vector<std::string> sent_;
};

class OrderService {
public:
    explicit OrderService(std::unique_ptr<Notifier> notifier) : notifier_(std::move(notifier)) {}
    void place(const std::string& item) { notifier_->notify("ordered " + item); }
private:
    std::unique_ptr<Notifier> notifier_;
};

int main() {
    OrderService svc(std::make_unique<ConsoleNotifier>());
    svc.place("pen");
}

What changed, and the trade-off

OrderService now states what it needs and owns the dependency through unique_ptr. Production wires ConsoleNotifier; tests wire RecordingNotifier and assert on sent(). Constructor injection also makes the dependency impossible to forget.

Trade-off: one more interface and explicit wiring in main. Use a reference (non-owning) when the caller keeps ownership, unique_ptr for exclusive ownership, and shared_ptr only for genuinely shared lifetime.

Say it in the interview

"I'll inject the clock and the store through constructors so I can unit-test the rules" is the sentence that separates an SDE II from a Senior who also says where the wiring lives (a composition root) and why a global singleton would hurt.

When it goes too far

Wrapping every library class (std::string, std::vector) behind your own interface is noise. Invert only across a real boundary: I/O, time, randomness, external services, or a part you expect to swap. A DI framework for a 300-line program is overkill; plain constructors do the job.
