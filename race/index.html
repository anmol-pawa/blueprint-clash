Schedule threads one step at a time to break a program, then let the explorer check every interleaving of the fix.

  • The lost updateInterleave the threads so both read the same value (a lost update), or let the explorer find the shortest bad schedule.
  • Opposite lock orderSchedule the threads into a deadlock, then fix it with a global lock order.
  • Check, then actFind the schedule in which both threads see the flag unset. The check and the action are separate steps, so nothing stops this.
  • An invariant across two variablesMake the auditor see a total other than 100, although every single access is atomic.
  • Claiming a slotGet both threads to believe they won, even though load and store are each atomic.
  • Waiting for a signalBreak each version: publish without the lock (lost wake-up), wake spuriously past an if, and then see why while (!ready) is the only safe form.
  • The ABA problemMake the Popper's compare-and-swap succeed against a stack that has changed underneath it, so top points at freed memory.
  • A bounded bufferShare one condition variable between 'not full' and 'not empty' and use notify_one: find the schedule where a wake-up goes to the wrong kind of waiter and everyone sleeps. (Spurious wake-ups are switched off here so the stuck state is visible; real code must still use while.)
  • Readers need the lock tooCatch the reader between the two writes. First without any lock on the reader, then with locks that are too small.
  • Double-checked lockingBreak it twice: first the plain pointer (a data race), then a relaxed atomic whose pointer store can become visible before the fields it points to.
  • Publishing data with a flagMake the consumer read data before it was written, or find the data race in the plain bool.
  • Too polite to finishFind the cycle in which both keep running, never deadlock, and never finish. The explorer reports a livelock only when every unfinished thread takes steps in the cycle.
