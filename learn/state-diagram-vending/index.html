State diagrams: events and states, not boolean flags

“If an object behaves differently over time, draw its states and events first, then make the code a closed set of states with one place that decides each transition.”

Vending machines, elevators, orders and documents all have a life cycle: a handful of states and a set of events that move between them. A state diagram shows each state as a box and each legal transition as an arrow labelled event [guard] / action.

Draw it before coding. The exercise exposes the cases requirements forgot: "what if a coin is inserted while dispensing?" is a missing arrow. In code, represent the states as an enum class (a closed set the compiler checks), the events as another, and keep every transition decision in one place. When states grow behaviour of their own, graduate to the State pattern (lesson in the Behavioural Theatre); for a small machine an enum and a switch is the honest, readable choice.

The smell

  • Several booleans (hasCoin_, dispensing_) that together encode the state, with impossible combinations the code never forbids.
  • Each method re-checks the flags in its own way, so a new rule must be added to every method.
  • Nobody can list the legal transitions without reading all of the code.
  • Events that should be rejected are silently ignored or crash.

Before

#include <iostream>

// State is spread over flags; nothing stops impossible combinations.
class Vending {
public:
    void insertCoin() {
        if (!hasCoin_ && !dispensing_) hasCoin_ = true;
        else std::cout << "ignored coin\n";
    }
    void press() {
        if (hasCoin_ && !dispensing_) { dispensing_ = true; hasCoin_ = false; std::cout << "dispensing\n"; }
        else std::cout << "nothing happens\n";
    }
    void take() {
        if (dispensing_) { dispensing_ = false; std::cout << "taken\n"; }
    }

private:
    bool hasCoin_ = false;
    bool dispensing_ = false;
};

int main() {
    Vending v;
    v.press();
    v.insertCoin();
    v.insertCoin();
    v.press();
    v.take();
}

After

#include <iostream>

// The state diagram, written down: a closed set of states and events, and one place that decides each transition.
enum class State { Idle, HasCoin, Dispensing };
enum class Event { InsertCoin, Press, Take };

class Vending {
public:
    void handle(Event event) {
        switch (state_) {
            case State::Idle:
                if (event == Event::InsertCoin) state_ = State::HasCoin;
                else std::cout << "nothing happens\n";
                break;
            case State::HasCoin:
                if (event == Event::Press) { state_ = State::Dispensing; std::cout << "dispensing\n"; }
                else if (event == Event::InsertCoin) std::cout << "ignored coin\n";
                else std::cout << "nothing happens\n";
                break;
            case State::Dispensing:
                if (event == Event::Take) { state_ = State::Idle; std::cout << "taken\n"; }
                else std::cout << "nothing happens\n";
                break;
        }
    }

private:
    State state_ = State::Idle;
};

int main() {
    Vending v;
    v.handle(Event::Press);
    v.handle(Event::InsertCoin);
    v.handle(Event::InsertCoin);
    v.handle(Event::Press);
    v.handle(Event::Take);
}

What changed, and the trade-off

The two flags became one State enum, so hasCoin and dispensing can no longer both be true. Every event goes through handle, which switches on the state, so the full transition list is readable in one screen and matches the diagram arrow for arrow. The observable behaviour is identical (the output did not change); the structure is what improved. Trade-off: a switch per state still has to be edited for each new state or event; once states carry behaviour of their own, the State pattern removes that.

Say it in the interview

Say "let me draw the states and events first". Name the states, list the events, and say what happens for each (state, event) pair, including the rejected ones. Level signal: SDE II gets the happy path; Senior covers the invalid transitions and the guard conditions; Staff discusses persistence of the state and concurrent events.

When it goes too far

A full State-pattern class hierarchy for a machine with three states and no state-specific data is ceremony. And a state diagram for something that has no real life cycle (a plain data record) adds nothing; draw one when behaviour depends on history.
