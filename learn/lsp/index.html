Liskov Substitution: honour the contract

“A subtype must keep every promise its base type makes, so callers never need to know which one they hold.”

Substitutability is about contracts, not syntax. A derived class may weaken preconditions (accept more) and strengthen postconditions (promise more), and must preserve the base's invariants. If code written against Base& can be broken by passing a Derived, inheritance was the wrong tool.

The classic trap: a mutable Square derived from Rectangle. Geometrically a square is a rectangle, but Rectangle promises "setting the width leaves the height alone", and Square cannot keep that promise.

The smell

  • An override that throws not supported or silently does nothing.
  • Callers that check dynamic_cast or a type tag before calling a base method.
  • A derived class that tightens an argument range the base accepted.
  • Documentation that says "except for subclass X".

Before

#include <iostream>

class Rectangle {
public:
    virtual ~Rectangle() = default;
    virtual void setWidth(int w) { w_ = w; }
    virtual void setHeight(int h) { h_ = h; }
    int area() const { return w_ * h_; }
protected:
    int w_ = 0;
    int h_ = 0;
};

// Breaks Rectangle's promise that width and height are independent.
class Square : public Rectangle {
public:
    void setWidth(int w) override { w_ = h_ = w; }
    void setHeight(int h) override { w_ = h_ = h; }
};

int stretchTo2x3(Rectangle& r) {
    r.setWidth(2);
    r.setHeight(3);
    return r.area();  // callers expect 6
}

int main() {
    Rectangle r;
    Square s;
    std::cout << stretchTo2x3(r) << " " << stretchTo2x3(s) << "\n";
}

After

#include <iostream>

// No inheritance between them: each type states its own contract.
class Shape {
public:
    virtual ~Shape() = default;
    virtual int area() const = 0;
};

class Rectangle : public Shape {
public:
    Rectangle(int w, int h) : w_(w), h_(h) {}
    int area() const override { return w_ * h_; }
private:
    int w_;
    int h_;
};

class Square : public Shape {
public:
    explicit Square(int side) : side_(side) {}
    int area() const override { return side_ * side_; }
private:
    int side_;
};

// Immutable values: callers build new shapes instead of mutating through a base reference.
int main() {
    Rectangle r(2, 3);
    Square s(3);
    std::cout << r.area() << " " << s.area() << "\n";
}

What changed, and the trade-off

The mutation that made the hierarchy unsound is gone: shapes are immutable, so there is no "set one dimension" promise to break. Both types satisfy the one contract they really share, area().

Trade-off: immutability means "resize" produces a new object. If you truly need mutation, keep Rectangle and Square as separate unrelated classes, or model Square as a Rectangle factory function, not a subtype.

Say it in the interview

Phrase it as a contract check: "can every caller of the base type survive this subtype?". Naming preconditions, postconditions and invariants unprompted is a clear SDE II to Senior signal. Spotting an LSP break in the candidate's own hierarchy mid-interview and fixing it is a strong one.

When it goes too far

Treating every inheritance relationship as suspect leads to avoiding polymorphism you genuinely need. The rule bites on behavioural subtyping; sharing code between related types is better done with composition, and a base class with a well-defined contract and a few overrides is fine.
