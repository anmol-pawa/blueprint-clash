You are writing the order core for a food-delivery startup in one city. Customers order from a restaurant's menu, the kitchen cooks, a courier brings it, and the order moves through a handful of stages until it arrives or somebody calls it off.

What you know so far:

- Restaurants have menus with prices. A customer orders a few items from one restaurant and is told the total up front.
- A restaurant accepts or turns down an order, cooks it and says when it is ready. A courier then collects it and hands it over.
- Customers change their minds. What that costs depends on how far the kitchen has got.
- Other parts of the product (notifications, analytics) want to know whenever an order changes stage.

Your task: design and implement it behind the `food::Food` interface in `api.h`. The hidden tests call only that interface. Ask the interviewer first: the brief is deliberately incomplete, and "who gets a ready order when no courier is free, and when does a cancel cost money?" is where most first drafts go wrong.

## Requirements
Functional: restaurants with menus; a customer orders items and is quoted the total (food plus a flat 299 delivery fee) up front; an **order state machine**, Placed, Accepted, Ready, PickedUp, Delivered, with Rejected and Cancelled as the other ends; the restaurant answers and finishes the food, the assigned courier collects and hands over, and every call checks UnknownOrder, then WrongParty, then InvalidState. A ready order goes to the **free courier with the lowest name**, or waits and is given to the next courier who becomes free, oldest order first. The customer can cancel until a courier has the food: free while Placed, 25 percent of the food while Accepted, the whole food once Ready, never the delivery fee. Anyone can **subscribe** to see every change of state. Hidden until asked: the dispatch and tie-break rules, the queue order, what cancelling costs and when, what exactly is announced. Non-goals: payment, geography, ETAs, ratings, persistence, thread safety (discussed).

**Change Storm 1, promo codes:** `makePromoFood(codes)` and `placeWithCode`. A percentage or a fixed amount comes off the food only, with a minimum order; the code's checks have their own order; the cancellation fee is charged on the discounted food. Revealable by asking whether customers will be able to use discount codes.

**Change Storm 2, kitchen capacity:** `makeBusyKitchens(codes, slots)`. An order holds one of a kitchen's cooking places from Accepted until it leaves Accepted, and `accept` on a full kitchen is `KitchenFull`. Revealable by asking whether a kitchen can take unlimited orders.

## Reference design
- `Menu` is what each restaurant sells; it knows nothing about orders.
- `OrderDesk` validates a request in the documented order, prices it (applying a code when there is one) and records the order.
- `OrderBook` keeps every order, owns the **table of legal moves** (`OrderLifecycle`) and is the one place a state changes (`move`), where it tells the listeners: the Observer subject.
- `CourierPool` knows who is free and holds the queue of ready orders without a courier. It records an assignment on the order but never changes its state.
- `CancellationFee` is a Strategy (`StageFee`) from the stage and the food to what the customer owes.
- `FoodImpl` is a thin facade: ask the book whether the move is legal, make it, tell the collaborator that cares.

The central decision is that **each thing that changes for a business reason has its own home**: what a cancellation costs (`CancellationFee`), which moves are legal (`OrderLifecycle`), who gets a ready order (`CourierPool`), and who needs to hear about it (listeners on `OrderBook`). The two storms then land in one place each.

**Storm 1 in the reference:** `PromoBook` and `Discount` (`PercentOff`, `AmountOff`) are new classes; `OrderDesk` applies the discount to the food before adding the delivery fee and stores the discounted food on the order, so the existing fee strategy needs no change at all. **Storm 2 in the reference:** `KitchenLoad` is a new class that subscribes to the book and counts orders entering and leaving Accepted; `accept` gains one line asking it for room, after the shared checks. The honest cost is that the load has to see every event: it is correct only because `OrderBook::move` is the only way a state changes.

## Alternatives
- **An `if` chain on the state in each operation.** Quicker for the base game, and every new operation then has its own idea of what is legal. A table in one place makes a wrong move a one-row diff.
- **A State class per stage.** The textbook shape, and worth it when each stage has behaviour of its own (a timer, a message, a different fee). Here the stages differ in which moves are allowed and in one fee, so the table plus a fee Strategy is smaller and as clear; this editorial would choose State objects the day Ready orders need a no-courier timer.
- **Courier assignment as a field scan:** loop over all orders to find the oldest unassigned one whenever a courier frees up. Correct and quadratic; the queue costs a `set`. It also hides the rule: the queue shows in one place that 'oldest' means lowest id.
- **Notifications called directly from each operation** (`notifier.send(...)` after each move). Three call sites become eight, and cancel is the one that gets forgotten. The Observer funnel is the same code written once.
- **A counter for kitchen load updated in `accept` and `ready`.** Passes Storm 2's happy path and fails the first time an order leaves Accepted another way (cancel). Deriving the count from the transitions is what makes the exits impossible to miss.

## Trade-offs
- **Table of moves versus State objects:** small and testable versus room to grow behaviour per stage.
- **Observer versus direct calls:** a callback is easy to add and easy to make slow; synchronous listeners run inside the transition, so a throwing or blocking listener hurts the order flow. Production moves to an event log (see follow-ups).
- **Fee on discounted food:** the customer never pays more in fees than the food cost; the cost is that the order must remember the discounted food, not just the total.
- **Lowest-name courier:** deterministic and testable, but not fair or smart. It is a placeholder for the real rule (distance, ETA, load), which is one class.

## What breaks at 10x
At ten times the volume the scans hurt first: `CourierPool::orderReady` walks every courier, and `OrderBook::find` is fine but the courier queue is global. Split dispatch per city, keep free couriers in an ordered set, and keep the waiting orders in a heap by id. The single-threaded listeners would be the next thing to fail: publish events after the transition, to a queue.

## Level signals
- **SDE II:** a correct state machine with the party and state checks in the right order, the courier queue working in the happy path, fees by stage, and the observer feed. Storm 1 done by adding a parameter.
- **Senior:** the table of moves and the single funnel for state changes, couriers and their queue behind their own class, the fee as a Strategy, the discount applied before the delivery fee, kitchen load derived from transitions. Both storms land in one class each.
- **Staff:** names the invariants (one courier one order, every exit from Accepted frees a place), says which need a lock or a conditional write, and sketches the move to an event log with consumers, a dispatch service and idempotent transitions, with the saga costs stated.

// Public API for the Food delivery problem. The hidden tests only use what is declared here.
// You implement food::makeFood() (in any of your .cpp files); everything behind it is your design.
#include <functional>
#include <memory>
#include <string>
#include <vector>

namespace food {

using OrderId = long long;
constexpr OrderId kNoOrder = 0;  // ids that are issued are always positive and never reused
using Money = long long;         // whole cents

constexpr Money kDeliveryFee = 299;      // added to every order, never discounted
constexpr int kMaxQuantity = 20;         // per line
constexpr int kCookingFeePercent = 25;   // of the food, when the customer cancels an Accepted order

enum class Status {
  Ok,
  InvalidRequest,     // empty name, no lines, a quantity outside 1..kMaxQuantity
  UnknownRestaurant,
  UnknownItem,        // a line names something that is not on that restaurant's menu
  UnknownOrder,
  WrongParty,         // the restaurant, courier or customer is not the one on this order
  InvalidState,       // the order is not in a state where this is allowed
  UnknownPromo,       // used from Change Storm 1
  PromoNotApplicable, // used from Change Storm 1
  KitchenFull,        // used from Change Storm 2
};

enum class OrderState { Placed, Accepted, Ready, PickedUp, Delivered, Rejected, Cancelled };

struct MenuItem {
  std::string name;
  Money price = 0;  // cents, at least 1
};

struct Line {
  std::string item;
  int quantity = 1;
};

struct PlaceResult {
  Status status = Status::Ok;
  OrderId order = kNoOrder;  // kNoOrder unless status is Ok
  Money total = 0;           // 0 unless status is Ok; food plus kDeliveryFee, fixed from now on
};

struct CancelResult {
  Status status = Status::Ok;
  Money fee = 0;  // what the customer is charged for cancelling; 0 unless status is Ok
};

struct OrderInfo {
  Status status = Status::Ok;  // UnknownOrder when no such order was ever issued
  OrderState state = OrderState::Placed;
  std::string customer;
  std::string restaurant;
  std::string courier;  // empty until a courier has been assigned; kept after delivery
  Money total = 0;
};

// Called once for every change of state of every order, in the order the changes happen. It is NOT called when a
// courier is assigned (that is not a change of state).
using Listener = std::function<void(OrderId, OrderState from, OrderState to)>;

class Food {
 public:
  virtual ~Food() = default;

  // Registers a restaurant and its menu. Returns false, changing nothing, for an empty name, a name already
  // registered, an empty menu, or a menu item with an empty name, a price below 1 or the same name as another item.
  virtual bool addRestaurant(const std::string& restaurant, const std::vector<MenuItem>& menu) = 0;

  // Registers a courier, who is free at once. Returns false for an empty or an already registered name. If an order
  // is waiting for a courier (see ready), the oldest one is given to the new courier.
  virtual bool registerCourier(const std::string& courier) = 0;

  // Adds a listener. Listeners are called in the order they were added.
  virtual void subscribe(Listener listener) = 0;

  // Places an order: food = sum of price * quantity over the lines (the same item may appear in several lines);
  // total = food + kDeliveryFee, fixed now. Checks in order: InvalidRequest, UnknownRestaurant, UnknownItem.
  // A failed call changes nothing. The order starts Placed.
  virtual PlaceResult place(const std::string& customer, const std::string& restaurant, const std::vector<Line>& lines) = 0;

  // Order lifecycle: Placed -> Accepted -> Ready -> PickedUp -> Delivered, or Rejected / Cancelled. Every call checks,
  // in this order: UnknownOrder, WrongParty (the caller is not this order's restaurant / courier / customer),
  // InvalidState. A failed call changes nothing.
  //
  // accept / reject: the RESTAURANT answers a Placed order. Placed -> Accepted, or Placed -> Rejected.
  // ready:           the RESTAURANT finishes cooking. Accepted -> Ready. The order is then given to the free courier
  //                  with the LOWEST NAME; with nobody free it waits, unassigned, and is given to the next courier
  //                  who becomes free (oldest waiting order first, by order id).
  // pickUp:          the order's ASSIGNED courier collects it. Ready -> PickedUp. (An unassigned order has no
  //                  assigned courier, so every courier gets WrongParty.)
  // deliver:         the same courier hands it over. PickedUp -> Delivered. The courier is free again and takes the
  //                  oldest waiting order, if any.
  virtual Status accept(OrderId order, const std::string& restaurant) = 0;
  virtual Status reject(OrderId order, const std::string& restaurant) = 0;
  virtual Status ready(OrderId order, const std::string& restaurant) = 0;
  virtual Status pickUp(OrderId order, const std::string& courier) = 0;
  virtual Status deliver(OrderId order, const std::string& courier) = 0;

  // The CUSTOMER cancels. Allowed from Placed (fee 0), Accepted (fee = food * kCookingFeePercent / 100, rounded down)
  // and Ready (fee = the whole food, the delivery fee is never charged). From PickedUp, Delivered, Rejected or
  // Cancelled it is InvalidState. Checks: UnknownOrder, WrongParty, InvalidState. A courier assigned to the order is
  // free again at once and takes the oldest waiting order; a waiting order is simply removed from the queue.
  virtual CancelResult cancel(OrderId order, const std::string& customer) = 0;

  // Orders are never forgotten, so finished orders can be inspected.
  virtual OrderInfo order(OrderId order) const = 0;
};

// Always returns a working system.
std::unique_ptr<Food> makeFood();

}  // namespace food

namespace food {

enum class PromoKind { PercentOff, AmountOff };

struct Promo {
  std::string code;
  PromoKind kind = PromoKind::PercentOff;
  int value = 0;           // PercentOff: 1..100. AmountOff: cents, at least 1.
  Money minimumFood = 0;   // the code only applies when the food (before the discount) is at least this much
};

class PromoFood : public Food {
 public:
  // Like place(), with a code. Checks in order: InvalidRequest (as for place, or an empty code), UnknownRestaurant,
  // UnknownItem, UnknownPromo, PromoNotApplicable (food below the code's minimum). The discount comes off the FOOD
  // only, never off kDeliveryFee: PercentOff takes food * value / 100 rounded down, AmountOff takes
  // min(value, food). total = food - discount + kDeliveryFee, fixed now. From then on, "the food" for the
  // cancellation fee is the DISCOUNTED food: what the customer would actually have paid the restaurant.
  virtual PlaceResult placeWithCode(const std::string& customer, const std::string& restaurant,
                                    const std::vector<Line>& lines, const std::string& code) = 0;
};

// Promo codes are fixed when the system is built. Invalid or repeated codes in the list are ignored (the first
// valid one wins). makeFood() has no codes and place() never discounts.
std::unique_ptr<PromoFood> makePromoFood(const std::vector<Promo>& promos);

}  // namespace food

// Couriers and the queue of ready orders that have none. Free couriers are found by lowest name; waiting orders go
// out oldest first. It records an assignment on the order, but never changes an order's state.
class CourierPool {
 public:
  explicit CourierPool(OrderBook& book) : book_(book) {}

  bool enroll(const std::string& courier) {
    if (courier.empty() || !holding_.emplace(courier, food::kNoOrder).second) return false;
    handOver(courier);
    return true;
  }

  void orderReady(food::OrderId id) {
    for (auto& [name, held] : holding_) {
      if (held != food::kNoOrder) continue;
      held = id;
      book_.assign(id, name);
      return;
    }
    waiting_.insert(id);
  }

  void orderDelivered(food::OrderId id) { handOver(book_.find(id)->courier); }

  void orderCancelled(food::OrderId id) {
    const std::string& courier = book_.find(id)->courier;
    if (courier.empty()) {
      waiting_.erase(id);
    } else {
      handOver(courier);
    }
  }

 private:
  // The courier is free; give them the oldest waiting order, if there is one.
  void handOver(const std::string& courier) {
    holding_[courier] = food::kNoOrder;
    if (waiting_.empty()) return;
    const food::OrderId next = *waiting_.begin();
    waiting_.erase(waiting_.begin());
    holding_[courier] = next;
    book_.assign(next, courier);
  }

  OrderBook& book_;
  std::map<std::string, food::OrderId> holding_;
  std::set<food::OrderId> waiting_;
};

struct Order {

// Who is asking for a move.
enum class Role { Restaurant, Courier, Customer };

// The state machine, written once as a table of legal moves.
class OrderLifecycle {
 public:
  static bool allows(food::OrderState from, food::OrderState to) {
    using food::OrderState;
    static const std::set<std::pair<OrderState, OrderState>> moves = {
        {OrderState::Placed, OrderState::Accepted},    {OrderState::Placed, OrderState::Rejected},
        {OrderState::Placed, OrderState::Cancelled},   {OrderState::Accepted, OrderState::Ready},
        {OrderState::Accepted, OrderState::Cancelled}, {OrderState::Ready, OrderState::PickedUp},
        {OrderState::Ready, OrderState::Cancelled},    {OrderState::PickedUp, OrderState::Delivered},
    };
    return moves.count({from, to}) > 0;
  }
};

// Keeps every order for good, issues ids, and is the ONE place where an order changes state: every change goes
// through move(), which tells the listeners (the Observer subject of the design).
class OrderBook {
 public:
  food::OrderId open(Order order) {
    const food::OrderId id = nextId_++;
    orders_.emplace(id, std::move(order));
    return id;
  }

  const Order* find(food::OrderId id) const {
    const auto found = orders_.find(id);
    return found == orders_.end() ? nullptr : &found->second;
  }

  void subscribe(food::Listener listener) { listeners_.push_back(std::move(listener)); }

  // The checks every lifecycle call shares, in the documented order. Changes nothing.
  food::Status check(food::OrderId id, Role role, const std::string& who, food::OrderState to) const {
    const Order* order = find(id);
    if (order == nullptr) return food::Status::UnknownOrder;
    if (!isParty(*order, role, who)) return food::Status::WrongParty;
    if (!OrderLifecycle::allows(order->state, to)) return food::Status::InvalidState;
    return food::Status::Ok;
  }

  void move(food::OrderId id, food::OrderState to) {
    Order& order = orders_.at(id);
    const food::OrderState from = order.state;
    order.state = to;
    for (const food::Listener& listener : listeners_) listener(id, from, to);
  }

  food::Status advance(food::OrderId id, Role role, const std::string& who, food::OrderState to) {
    const food::Status status = check(id, role, who, to);
    if (status == food::Status::Ok) move(id, to);
    return status;
  }

  void assign(food::OrderId id, const std::string& courier) { orders_.at(id).courier = courier; }

 private:
  static bool isParty(const Order& order, Role role, const std::string& who) {
    switch (role) {
      case Role::Restaurant: return order.restaurant == who;
      case Role::Customer: return order.customer == who;
      case Role::Courier: return !order.courier.empty() && order.courier == who;
    }
    return false;
  }

  food::OrderId nextId_ = 1;
  std::map<food::OrderId, Order> orders_;
  std::vector<food::Listener> listeners_;
};
