1b:T21f0,# Editorial: Splitwise (expense sharing)

## Requirements
Functional: `addMember(name)` builds the group. `addExpense(payer, cents, participants)` says who paid and who shared the bill equally; each participant other than the payer now owes the payer their portion. `balance(member)` and `owed(from, to)` report the position of one person and the net direct debt between two. `settleUp(from, to, cents)` records real money moving. Amounts are whole cents between 1 and `kMaxCents`. Hidden until asked: how the odd cents are handed out (the first `cents % n` participants in the order given pay one more, so portions always add up), that the payer need not take part, the order of the checks (amount, participants, membership, duplicates) and that a refused expense changes nothing, that `owed` cancels the opposite direction, and that paying more than is owed turns the debt around. Non-goals: threads, persistence, editing history, several currencies, a user interface.

**Change Storm 1, unequal splits:** `makeSplitLedger`: `addExpenseWith(payer, cents, spec)` takes a kind: Equal as before, Exact (each share's cents, which must add up to the bill) or Percent (basis points that add up to 10000). The same four checks, then `BadSplit`. A percent portion is `cents * value / 10000` rounded down and the leftover cents go to the largest remainders, ties to the member listed first. Revealable by asking whether people will want to split in other ways than equally.

**Change Storm 2, simplifying debts:** `makeSimplifyingLedger`: `simplify()` returns payments that bring every balance to zero. It works from net balances, never changes the ledger, and is greedy: the largest debtor (ties by name) pays the largest creditor (ties by name) the smaller amount, repeatedly. Revealable by asking whether the app will need a short list of payments.

## Reference design
- `Members` owns who is in the group: unique, non-empty names and the membership test.
- `SplitRule` is the Strategy that turns one bill into portions: `apportion(cents, shares, portions)` returns false when the numbers make no sense for that rule and otherwise guarantees the portions add up to the bill. `EqualSplit` is the base rule. `SplitRules` is the small registry that finds a rule by kind.
- `DebtBook` owns the money. It stores directed debts and never edits them: an expense adds `participant owes payer`, and a payment `from -> to` is recorded as `to owes from` (so a payment is the opposite of an expense and over-payment needs no special case). `owed` cancels the opposite direction and `balance` sums what is owed to a member minus what the member owes.
- `LedgerImpl` is the facade: it checks a request in the documented order, asks the rule for portions, tells the book who owes whom and answers queries. It has no rule of its own about rounding, netting or planning, and it validates everything before writing anything, which is how a refused expense changes nothing.

**Storm 1 in the reference:** two new classes, `ExactSplit` and `PercentSplit`, registered in `SplitRules`. Neither the equal rule nor `DebtBook` is touched, and the facade only gained `addExpenseWith` (the old `addExpense` now calls it with an equal spec). The honest cost is that the registry is a place that lists every kind, so adding a kind is "one class and one line", not "one class".

**Storm 2 in the reference:** one new class, `DebtSimplifier`, a pure function from balances to a list of `Transfer`. The facade collects the balances and calls it; nothing is mutated, which is why a plan is safe to compute on every screen refresh. The plan needs the sorted member list, which `Members` already offered.

## Alternatives
- **A single `Expense` record with a `std::vector<double>` of portions** is the first draft most people write. It fails on money (floating point), puts the rounding in whichever line divides, and loses the invariant that the portions add up. Integers plus an explicit remainder rule fix all three.
- **A graph of balances kept up to date** (`balance[a][b]` mutated on every expense and payment) is a respectable design and what many apps do. It is faster to read and loses the event history; a payment that exceeds the debt needs a sign flip in the middle of the update. Storing directed debts and deriving the net keeps the writes trivial at the cost of an O(entries) read, which a running balance per member can remove when needed.
- **A `switch` on the split kind inside `addExpense`** is the shortest thing that works for the first two kinds. It is the shape the Change Storm punishes: every new kind (shares, by item, with tax) edits the one function that also does validation and bookkeeping. A strategy interface with a registry confines each rule to its own class, at the price of one more abstraction to explain.
- **Minimum-transaction settlement** instead of greedy is the textbook answer to the simplification question. It is NP-hard in general (it contains subset-sum); for a group of ten, a search over subsets is cheap, for thousands it is not, and the saving over greedy is usually one payment. The reference takes greedy for its determinism and says so.
- **Floating-point money with a rounding helper at the end** hides the cent-handling in one place and still accumulates error in the sums. Never an acceptable answer in a ledger.
- **Editing an expense in place** is simpler to code and impossible to audit. The append-only approach (reverse the old entry, add the new one) is the answer to follow-ups about history.

## Trade-offs
Integers make every statement testable with equality, at the cost of choosing a currency scale up front and being explicit about rounding. Handing the extra cents to the first listed names is deterministic and easy to explain, and slightly unfair to whoever is always listed first; rotating the favour needs state, and the payer absorbing it hides the problem rather than solving it. Refusing instead of repairing (a duplicate name, a percentage total of 99.99) pushes errors back to the caller where the user can see them, rather than guessing what they meant. Netting pairwise debts is what users expect to see ("I owe Sam 12.50"), while simplifying uses only net positions and so may ask someone to pay a person they never owed; that is a product choice and the app should show the pairwise and simplified views side by side, not silently replace one with the other. Greedy simplification is not minimal but is predictable, which matters when two clients must show the same plan.

## What breaks at 10x
At 10x the expenses per group, reading a balance by scanning every debt becomes the cost; keep a running net per member, updated with each event and verifiable against the log. At 10x the members, `simplify()` is O(n^2) with the simple scan for the largest party; two heaps make it O(n log n). At 10x the groups, one process per group stops being enough: shard by group id, keep every invariant inside one shard, and persist the event log. At 10x the clients, expenses arrive from several phones and retries: give each expense a client-generated id so a repeated request is idempotent, and decide how concurrent edits merge. At 10x the money, you meet currencies, payment providers and tax rules: each is a new kind of event with its own reconciliation, which is another reason to keep the log of events as the source of truth.

## Level signals
- **SDE2:** a working ledger with members, an expense that splits equally, and a way to read what someone owes; uses integers or is helped to; handles the odd cent after a prompt; pairwise `owed` may double-count opposite debts until asked; the unequal splits come as a switch or an extra parameter.
- **Senior:** asks about money representation, rounding, the payer's own share and what a refused expense does; keeps the portions exactly equal to the bill; separates the split rule, the money book and the facade; records a payment as the opposite of an expense; nets pairwise debts in one place; adds exact and percent splits as new classes behind a strategy and explains largest remainder; builds simplification as a pure function from balances and states what greedy does and does not promise.
- **Staff:** puts the contract first (every balance is derived from an append-only event log, and the invariant is that balances sum to zero); explains why minimum settlement is NP-hard and why that rarely matters; plans the move to a sharded service with idempotent writes, optimistic concurrency and per-currency books; separates the pairwise view from the simplified view as a product decision; considers reconciling with a payment provider and what a failed or duplicated payment does to the book.

// Public API for the Splitwise problem. The hidden tests only use what is declared here.
// You implement split::makeLedger() (in any of your .cpp files); everything behind it is your design.
// Nothing here throws: this code is compiled without exceptions.
#include <memory>
#include <string>
#include <vector>

namespace split {

// Money is a whole number of cents (no floating point). Every amount is in 1 .. kMaxCents.
constexpr long long kMaxCents = 1000000000000LL;

enum class Status {
  Ok,
  InvalidAmount,         // the amount is below 1 or above kMaxCents
  NoParticipants,        // an expense with nobody to share it
  UnknownMember,         // the payer, a participant, or a settling party is not a member
  DuplicateParticipant,  // the same member is listed twice in one expense
  SameMember,            // settleUp(a, a)
  BadSplit,              // the listed split values do not describe a valid split (not produced by an equal split)
};

class Ledger {
 public:
  virtual ~Ledger() = default;

  // Adds a person to the group. Returns false (and changes nothing) for an empty name or a name already present.
  virtual bool addMember(const std::string& name) = 0;

  // `payer` paid `cents` for everyone in `participants`, who share it equally. The payer need not be a participant.
  // When the cents do not divide evenly, the first (cents % n) participants in the order given pay one cent more.
  // Checks run in this order and the first failure decides, changing nothing:
  //   1. cents outside 1 .. kMaxCents      -> InvalidAmount
  //   2. no participants                   -> NoParticipants
  //   3. the payer or a participant is not a member -> UnknownMember
  //   4. a participant listed twice        -> DuplicateParticipant
  // Participants other than the payer now owe the payer their share. The payer owes nothing to themselves.
  virtual Status addExpense(const std::string& payer, long long cents, const std::vector<std::string>& participants) = 0;

  // `from` pays `to` `cents` in real money, which reduces what `from` owes `to`. Paying more than is owed is allowed:
  // the debt turns around and `to` now owes `from` the difference. Checks, in order: cents outside 1 .. kMaxCents ->
  // InvalidAmount; either name is not a member -> UnknownMember; from == to -> SameMember.
  virtual Status settleUp(const std::string& from, const std::string& to, long long cents) = 0;

  // What the group owes this member (positive) or what this member owes the group (negative), in cents. The balances of
  // all members always add up to zero. An unknown name has balance 0.
  virtual long long balance(const std::string& member) const = 0;

  // What `from` owes `to` directly, after cancelling anything `to` owes `from` the other way round. Never negative; at
  // most one of owed(a, b) and owed(b, a) is non-zero. Unknown names owe nothing.
  virtual long long owed(const std::string& from, const std::string& to) const = 0;
};

std::unique_ptr<Ledger> makeLedger();

}  // namespace split

// "Whole" for a percentage: 10000 basis points = 100.00%.
constexpr long long kWhole = 10000;

enum class SplitKind {
  Equal,    // as addExpense: the values in the shares are ignored
  Exact,    // each share's value is its cents
  Percent,  // each share's value is its portion in basis points (2500 = 25.00%)
};

struct Share {
  std::string member;
  long long value = 0;
};

struct SplitSpec {
  SplitKind kind = SplitKind::Equal;
  std::vector<Share> shares;  // who takes part, in order, and (for Exact and Percent) how much
};

// A ledger that can split an expense in more ways than equally.
//   - addExpenseWith(payer, cents, spec) runs the same four checks as addExpense, in the same order, on the shares'
//     members, and then one more: BadSplit when
//       Exact:   any value is negative, or the values do not add up to `cents` exactly;
//       Percent: any value is negative or above kWhole, or the values do not add up to kWhole exactly.
//     Equal never gives BadSplit. A refused expense changes nothing.
//   - Percent: a member's portion is cents * value / kWhole rounded down; the cents left over (always fewer than the
//     number of shares) go one each to the members with the largest fractional remainder, a tie going to the one listed
//     first. The portions always add up to `cents`.
//   - Everything else (who owes whom, balances, settleUp) works as before. addExpense keeps working.
class SplitLedger : public Ledger {
 public:
  virtual Status addExpenseWith(const std::string& payer, long long cents, const SplitSpec& spec) = 0;
};

std::unique_ptr<SplitLedger> makeSplitLedger();

}  // namespace split

// Who owes whom, in cents. Debts are stored per direction and never edited in place: a payment is recorded as a debt the
// other way round, so the book is a plain sum of events and the net figures are derived.
class DebtBook {
 public:
  // `debtor` owes `creditor` another `cents`.
  void owe(const std::string& debtor, const std::string& creditor, long long cents) {
    if (cents > 0) debts_[{debtor, creditor}] += cents;
  }

  // `from` hands `to` `cents`, which is the same as `to` owing `from` that much more.
  void pay(const std::string& from, const std::string& to, long long cents) { owe(to, from, cents); }

  // What `from` owes `to` once the opposite direction has been cancelled. Never negative.
  long long owed(const std::string& from, const std::string& to) const {
    return std::max(0LL, directed(from, to) - directed(to, from));
  }

  // Positive when others owe this member overall, negative when this member owes.
  long long balance(const std::string& member) const {
    long long total = 0;
    for (const auto& entry : debts_) {
      if (entry.first.second == member) total += entry.second;
      if (entry.first.first == member) total -= entry.second;
    }
    return total;
  }

 private:
  long long directed(const std::string& debtor, const std::string& creditor) const {
    const auto found = debts_.find({debtor, creditor});
    return found == debts_.end() ? 0 : found->second;
  }

  std::map<std::pair<std::string, std::string>, long long> debts_;
};

// Turns balances into a short list of payments. It is a pure function of the balances: it knows nothing about expenses.
// Greedy: the largest debtor pays the largest creditor as much as they can, until nobody owes. That never needs more than
// (people with a balance) - 1 payments. A minimum is NP-hard (it contains subset-sum), so the greedy plan is not always
// the smallest, only always small, quick and easy to explain.
class DebtSimplifier {
 public:
  // positive balance = is owed, negative = owes. Zero balances may be present and are ignored.
  std::vector<split::Transfer> plan(const std::map<std::string, long long>& balances) const {
    std::vector<Party> debtors = side(balances, -1);
    std::vector<Party> creditors = side(balances, 1);
    std::vector<split::Transfer> transfers;
    while (!debtors.empty() && !creditors.empty()) {
      Party& debtor = *largest(debtors);
      Party& creditor = *largest(creditors);
      const long long amount = std::min(debtor.cents, creditor.cents);
      transfers.push_back(split::Transfer{debtor.name, creditor.name, amount});
      debtor.cents -= amount;
      creditor.cents -= amount;
      dropSettled(debtors);
      dropSettled(creditors);
    }
    return transfers;
  }

 private:
  struct Party {
    std::string name;
    long long cents;  // always positive: how much this party still has to pay or to receive
  };

  static std::vector<Party> side(const std::map<std::string, long long>& balances, int sign) {
    std::vector<Party> parties;
    for (const auto& entry : balances) {
      const long long cents = sign * entry.second;
      if (cents > 0) parties.push_back(Party{entry.first, cents});
    }
    return parties;
  }

  // The most money, and among equals the name that sorts first.
  static std::vector<Party>::iterator largest(std::vector<Party>& parties) {
    return std::max_element(parties.begin(), parties.end(), [](const Party& a, const Party& b) {
      return a.cents < b.cents || (a.cents == b.cents && a.name > b.name);
    });
  }

  static void dropSettled(std::vector<Party>& parties) {
    parties.erase(std::remove_if(parties.begin(), parties.end(), [](const Party& p) { return p.cents == 0; }), parties.end());
  }
};

    }

  }

  DebtSimplifier simplifier_;

// How one expense is cut into portions: portions[i] is what shares[i].member owes. A rule returns false when the listed
// values make no sense for it; when it returns true the portions add up to the expense exactly (no cent is lost).
class SplitRule {
 public:
  virtual ~SplitRule() = default;
  virtual bool apportion(long long cents, const std::vector<split::Share>& shares, std::vector<long long>& portions) const = 0;
};

// Everyone pays the same; the leftover cents go one each to the first names in the list.
class EqualSplit : public SplitRule {
 public:
  bool apportion(long long cents, const std::vector<split::Share>& shares, std::vector<long long>& portions) const override {
    const long long count = static_cast<long long>(shares.size());
    portions.assign(shares.size(), cents / count);
    const long long leftover = cents % count;
    for (long long i = 0; i < leftover; ++i) ++portions[static_cast<std::size_t>(i)];
    return true;
  }
};

// Each share names its own cents, which must add up to the expense.
class ExactSplit : public SplitRule {
 public:
  bool apportion(long long cents, const std::vector<split::Share>& shares, std::vector<long long>& portions) const override {
    long long total = 0;
    for (const split::Share& share : shares) {
      if (share.value < 0 || share.value > cents) return false;
      total += share.value;
    }
    if (total != cents) return false;
    portions.clear();
    for (const split::Share& share : shares) portions.push_back(share.value);
    return true;
  }
};

// Each share names a portion in basis points, which must add up to the whole. Rounded down, then the leftover cents go
// to the largest remainders (the "largest remainder" method), so the total is exact and nobody is shorted by more than a cent.
class PercentSplit : public SplitRule {
 public:
  bool apportion(long long cents, const std::vector<split::Share>& shares, std::vector<long long>& portions) const override {
    long long whole = 0;
    for (const split::Share& share : shares) {
      if (share.value < 0 || share.value > split::kWhole) return false;
      whole += share.value;
    }
    if (whole != split::kWhole) return false;
    portions.assign(shares.size(), 0);
    std::vector<long long> remainders(shares.size(), 0);
    long long given = 0;
    for (std::size_t i = 0; i < shares.size(); ++i) {
      const long long scaled = cents * shares[i].value;
      portions[i] = scaled / split::kWhole;
      remainders[i] = scaled % split::kWhole;
      given += portions[i];
    }
    handOutLeftover(cents - given, remainders, portions);
    return true;
  }

 private:
  static void handOutLeftover(long long leftover, const std::vector<long long>& remainders, std::vector<long long>& portions) {
    std::vector<std::size_t> order(remainders.size());
    std::iota(order.begin(), order.end(), static_cast<std::size_t>(0));
    std::stable_sort(order.begin(), order.end(), [&remainders](std::size_t a, std::size_t b) { return remainders[a] > remainders[b]; });
    for (long long k = 0; k < leftover; ++k) ++portions[order[static_cast<std::size_t>(k)]];
  }
};

class SplitRules {

    rules_[split::SplitKind::Percent] = std::make_unique<PercentSplit>();
  }

  const SplitRule* find(split::SplitKind kind) const {
    const auto found = rules_.find(kind);
    return found == rules_.end() ? nullptr : found->second.get();
  }

 private:
  std::map<split::SplitKind, std::unique_ptr<SplitRule>> rules_;
