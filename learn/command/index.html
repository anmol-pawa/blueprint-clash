Command: turn an action into an object you can store and undo

“Wrap a request as an object with execute and undo so it can be queued, logged, repeated and reversed.”

A Command is a request packaged as an object. It knows its receiver, carries the arguments, and exposes execute(), usually with undo(). Because it is a value you can hold, you can put it in a list: that gives you history, undo/redo, queues, macros, retry and audit logs.

Undo has two honest designs. A command can store what it needs to reverse itself (an AppendCommand remembers the text it added), which is small and fast. Or a command can capture a snapshot (Memento) of the state before it runs, which is simpler for complex edits and costs memory. Pick per command and say why.

A new command after an undo must clear the redo stack; otherwise redo would replay something that no longer follows from the current state. Invoker, command and receiver are the three roles interviewers expect you to name: the invoker (a History or a button) calls the command, which acts on the receiver (the Document).

The smell

  • UI handlers call the model directly, so there is no single place to record what was done.
  • "Undo" is requested but nothing remembers the actions, or each action snapshots the whole state.
  • Retry, queueing or macros would need every caller rewritten.
  • A giant switch that interprets action codes.

Before

#include <iostream>
#include <string>

class Document {
public:
    void append(const std::string& s) { text_ += s; }
    const std::string& text() const { return text_; }

private:
    std::string text_;
};

// Callers mutate the document directly, so nothing records what happened and undo is impossible.
int main() {
    Document doc;
    doc.append("hello");
    doc.append(" world");
    std::cout << doc.text() << "\n";
}

After

#include <cstddef>
#include <iostream>
#include <memory>
#include <string>
#include <utility>
#include <vector>

// The receiver.
class Document {
public:
    void append(const std::string& s) { text_ += s; }
    void truncate(std::size_t n) { text_.resize(n < text_.size() ? text_.size() - n : 0); }
    const std::string& text() const { return text_; }

private:
    std::string text_;
};

class Command {
public:
    virtual ~Command() = default;
    virtual void execute() = 0;
    virtual void undo() = 0;
};

// Stores exactly what it needs to reverse itself. The document must outlive the command.
class AppendCommand : public Command {
public:
    AppendCommand(Document& doc, std::string text) : doc_(doc), text_(std::move(text)) {}
    void execute() override { doc_.append(text_); }
    void undo() override { doc_.truncate(text_.size()); }

private:
    Document& doc_;
    std::string text_;
};

// The invoker: runs commands and keeps the two stacks.
class History {
public:
    void run(std::unique_ptr<Command> command) {
        command->execute();
        undoStack_.push_back(std::move(command));
        redoStack_.clear();  // a new action invalidates the old future
    }

    bool undo() {
        if (undoStack_.empty()) return false;
        auto command = std::move(undoStack_.back());
        undoStack_.pop_back();
        command->undo();
        redoStack_.push_back(std::move(command));
        return true;
    }

    bool redo() {
        if (redoStack_.empty()) return false;
        auto command = std::move(redoStack_.back());
        redoStack_.pop_back();
        command->execute();
        undoStack_.push_back(std::move(command));
        return true;
    }

private:
    std::vector<std::unique_ptr<Command>> undoStack_;
    std::vector<std::unique_ptr<Command>> redoStack_;
};

int main() {
    Document doc;
    History history;
    history.run(std::make_unique<AppendCommand>(doc, "hello"));
    history.run(std::make_unique<AppendCommand>(doc, " world"));
    std::cout << doc.text() << "\n";
    history.undo();
    std::cout << doc.text() << "\n";
    history.redo();
    std::cout << doc.text() << "\n";
    history.undo();
    history.undo();
    std::cout << "[" << doc.text() << "]\n";
    std::cout << (history.undo() ? "undone" : "nothing to undo") << "\n";
}

What changed, and the trade-off

Every edit goes through History::run, so undo, redo, and (later) logging or macro recording are one place. Adding a DeleteCommand touches neither History nor the existing commands. Ownership is explicit: the history owns commands through unique_ptr; a command only references its receiver.

Trade-offs: one object per action means allocation and memory growth, so real editors cap history or coalesce typing into one command. A command that stores a reference to its receiver is only valid while the receiver lives; if commands can outlive it, hold an id or a weak_ptr. A command's undo() must exactly invert execute(); commands that cannot be reversed (sending an email) should say so rather than pretend.

Say it in the interview

Say "I need to record and reverse actions, so each action becomes an object". Name the roles (invoker, command, receiver), show two stacks, and volunteer that a fresh command clears redo. Senior signal: you compare storing a delta with a Memento snapshot, mention coalescing and history limits, and connect Command to queues, retries, idempotency keys and event sourcing in system design.

When it goes too far

A command class per button press is ceremony when nothing needs undo, queueing or logging; a plain method call or lambda does the job. Commands that duplicate their receiver's whole API turn into a second copy of the model. If a "command" is really a long-running workflow with steps that can fail halfway, you want a saga or a transaction, not a bigger Command.
