Requirements to entities: nouns, verbs and CRC cards

“Underline the nouns and verbs in the brief, make the nouns classes, and give each verb to the class that already holds the data it needs.”

A machine-coding or LLD round starts with a paragraph of requirements, not a class list. The reliable first step is noun/verb analysis: underline the nouns (candidate classes or fields) and the verbs (candidate methods), then discard the noise. Nouns that only describe another noun ("name", "title") are fields; nouns with their own rules and lifecycle ("loan", "fine policy") are classes.

Then run CRC cards (Class, Responsibility, Collaborators) on each candidate: one sentence for what it is responsible for, and which other classes it must ask for help. A class with a long, vague responsibility is two classes. A class with no responsibility was a field. A verb that needs data from three classes belongs to an orchestrating class, not to one of the three.

The output of this step is the vocabulary of the whole interview: the entities you name now are the ones the interviewer will ask you to extend.

The smell

  • One class named after the whole system (Library, Manager, Service) holds every map and every rule.
  • Entities exist only as parallel maps keyed by an id (dueDay_[bookId], holder_[bookId]).
  • A business rule (the fine) is buried inside a method, with no name and no place to change it.
  • You cannot say what a class is responsible for in one sentence without the word "and".

Before

#include <iostream>
#include <map>
#include <string>

// One class does everything the brief mentions: members, books, loans, fines.
class Library {
public:
    void addBook(int id) { copies_[id] = true; }
    void borrow(const std::string& member, int bookId, int day) {
        if (!copies_[bookId]) { std::cout << "book " << bookId << " unavailable\n"; return; }
        copies_[bookId] = false;
        dueDay_[bookId] = day + 14;
        holder_[bookId] = member;
    }
    int giveBack(int bookId, int day) {
        copies_[bookId] = true;
        int late = day - dueDay_[bookId];
        return late > 0 ? late * 10 : 0;  // fine policy hidden inside
    }

private:
    std::map<int, bool> copies_;
    std::map<int, int> dueDay_;
    std::map<int, std::string> holder_;
};

int main() {
    Library library;
    library.addBook(1);
    library.borrow("asha", 1, 0);
    library.borrow("ben", 1, 2);
    std::cout << "fine " << library.giveBack(1, 20) << "\n";
}

After

#include <iostream>
#include <string>
#include <utility>
#include <vector>

// Nouns from the brief became classes; each verb went to the noun that owns the data it needs (CRC).
class Book {
public:
    explicit Book(int id) : id_(id) {}
    int id() const { return id_; }
    bool available() const { return available_; }
    void lend() { available_ = false; }
    void restore() { available_ = true; }

private:
    int id_;
    bool available_ = true;
};

class Loan {
public:
    Loan(std::string member, int bookId, int dueDay) : member_(std::move(member)), bookId_(bookId), dueDay_(dueDay) {}
    int bookId() const { return bookId_; }
    int daysLate(int today) const { return today > dueDay_ ? today - dueDay_ : 0; }

private:
    std::string member_;
    int bookId_;
    int dueDay_;
};

// The fine rule is a policy of its own, because "what do late returns cost" is the likeliest thing to change.
class FinePolicy {
public:
    explicit FinePolicy(int perDay) : perDay_(perDay) {}
    int fineFor(const Loan& loan, int today) const { return loan.daysLate(today) * perDay_; }

private:
    int perDay_;
};

class Library {
public:
    explicit Library(FinePolicy policy) : policy_(policy) {}
    void addBook(int id) { books_.emplace_back(id); }

    void borrow(const std::string& member, int bookId, int day) {
        Book* book = find(bookId);
        if (book == nullptr || !book->available()) {
            std::cout << "book " << bookId << " unavailable\n";
            return;
        }
        book->lend();
        loans_.emplace_back(member, bookId, day + 14);
    }

    int giveBack(int bookId, int day) {
        Book* book = find(bookId);
        for (auto it = loans_.begin(); it != loans_.end(); ++it) {
            if (it->bookId() == bookId) {
                const int fine = policy_.fineFor(*it, day);
                loans_.erase(it);
                if (book != nullptr) book->restore();
                return fine;
            }
        }
        return 0;
    }

private:
    Book* find(int id) {
        for (auto& book : books_) {
            if (book.id() == id) return &book;
        }
        return nullptr;
    }

    FinePolicy policy_;
    std::vector<Book> books_;
    std::vector<Loan> loans_;
};

int main() {
    Library library{FinePolicy{10}};
    library.addBook(1);
    library.borrow("asha", 1, 0);
    library.borrow("ben", 1, 2);
    std::cout << "fine " << library.giveBack(1, 20) << "\n";
}

What changed, and the trade-off

The brief's nouns (book, loan, fine policy, library) are now classes, and each verb moved to the noun that owns its data: Loan::daysLate, FinePolicy::fineFor, Book::lend. The parallel maps became one Loan object per loan. Library is still the coordinator, but now it only coordinates. The fine rule has a name and one place to change, which is exactly the Change Storm an interviewer is likely to throw ("fines double after 30 days"). Trade-off: more types and more lines for a small problem; do this when the brief has real rules, not for a three-field record.

Say it in the interview

Say the process aloud: "nouns to candidate classes, verbs to methods, then I check each class has one responsibility and list its collaborators." Draw three or four CRC cards on the board before any code. Level signal: SDE II names sensible entities; Senior also names the policy that is likely to change and keeps it separate; Staff states what is deliberately left out of scope and why.

When it goes too far

Turning every noun into a class produces dozens of anaemic wrappers (MemberName, BookTitle) that hold one field and no behaviour. A noun earns a class only when it has rules, a lifecycle or more than one implementation. In a 45-minute round, five or six well-chosen entities beat fifteen thin ones.
