Memento: save and restore state without breaking encapsulation

“Capture an object's state in an opaque token so it can be restored later, without exposing its internals.”

A Memento is a sealed snapshot of an object's state. The object (the originator) creates it and is the only one who can read it; a caretaker (an undo history, a save slot) stores it and hands it back, without ever looking inside. That is what makes undo possible without making every field public.

The roles: the originator has save() and restore(snapshot); the memento is a small value type with a private constructor and a friend (or nested-class access) for the originator only; the caretaker keeps a stack of mementos. In C++ a nested Snapshot class with a private constructor and friend class Editor; gives exactly this.

Mementos are an alternative to Command-with-undo. Command stores how to reverse an action; Memento stores what the state was. Memento is simpler when reversing is hard or the state is small; Command is cheaper when the state is large and the change is tiny.

The smell

  • Fields are public (or have setters for everything) just so another class can save and restore them.
  • The save code lives in the caller and has to list every field; adding a field silently breaks undo.
  • A restore brings back some fields and forgets others, leaving an inconsistent object (a cursor past the end of the text).
  • The history class knows the editor's internals.

Before

#include <iostream>
#include <string>

// Every field is public, so the caller does the saving, and has to remember every field.
class Editor {
public:
    std::string text;
    int cursor = 0;
};

int main() {
    Editor editor;
    editor.text = "hello";
    editor.cursor = 5;

    std::string savedText = editor.text;  // the caller copies the insides...
    editor.text += " world";
    editor.cursor = 11;

    editor.text = savedText;  // ...and forgets the cursor when restoring
    std::cout << editor.text << " cursor " << editor.cursor << "\n";
}

After

#include <iostream>
#include <string>
#include <utility>
#include <vector>

class Editor {
public:
    // An opaque token: only Editor can build one or read it. History just carries it.
    class Snapshot {
    private:
        friend class Editor;
        Snapshot(std::string text, std::size_t cursor) : text_(std::move(text)), cursor_(cursor) {}
        std::string text_;
        std::size_t cursor_;
    };

    void type(const std::string& more) {
        text_ += more;
        cursor_ = text_.size();
    }
    Snapshot save() const { return Snapshot(text_, cursor_); }
    void restore(const Snapshot& snapshot) {
        text_ = snapshot.text_;
        cursor_ = snapshot.cursor_;
    }
    void print() const { std::cout << text_ << " cursor " << cursor_ << "\n"; }

private:
    std::string text_;
    std::size_t cursor_ = 0;
};

class History {
public:
    void push(Editor::Snapshot snapshot) { snapshots_.push_back(std::move(snapshot)); }
    bool empty() const { return snapshots_.empty(); }
    Editor::Snapshot pop() {
        Editor::Snapshot last = std::move(snapshots_.back());
        snapshots_.pop_back();
        return last;
    }

private:
    std::vector<Editor::Snapshot> snapshots_;
};

int main() {
    Editor editor;
    History history;
    editor.type("hello");
    history.push(editor.save());
    editor.type(" world");
    editor.print();
    if (!history.empty()) editor.restore(history.pop());
    editor.print();
}

What changed, and the trade-off

The caller used to copy text and forget cursor; now save() captures every field in one place, next to the fields, so a new field is added to the snapshot in the same edit. The Snapshot constructor is private and only Editor is a friend, so History can store and return snapshots but cannot read or forge one. The fields are private again.

Trade-offs: a snapshot copies the whole state, so a big document times a long history is memory-hungry. Options are to store diffs (then you are close to Command), to cap the history, or to share unchanged parts (persistent data structures). Mementos also freeze invariants at one moment: restoring a snapshot into an object whose environment has moved on (a file that was deleted) needs care. If the snapshot must outlive the program (save files), you have a serialisation format and a versioning problem, which is a different design.

Say it in the interview

Name the three roles, then say "the history never sees inside the snapshot". In an editor, text-box or game-save question, point at the encapsulation win (private fields, one save()), then offer the cost model: full copy versus deltas, with a cap on history depth. Senior signal: you compare it with Command-based undo, say which you would pick for this size of state, and mention what happens to redo (clear it on a new edit).

When it goes too far

Snapshotting a large object on every keystroke is a performance bug. If the state is two integers, passing them back is simpler. A memento that exposes getters for the caretaker to "peek" has lost its point. And if only one operation needs undo, a single reverse function is lighter than a whole snapshot protocol.
