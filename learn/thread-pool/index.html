Thread pool: fixed workers, a queue, and a clean shutdown

“Create a few workers once and feed them tasks through a mutex-guarded queue, instead of paying for a thread per task.”

A thread per task costs a stack, a kernel object and scheduling work each time, and an unbounded number of threads can exhaust memory or thrash the scheduler. A thread pool keeps a fixed set of workers alive and hands them tasks through a queue. It is the standard "build me X" in a machine-coding round because it combines everything in this district: a mutex, a condition variable with a predicate, ownership of threads, and a shutdown protocol.

The moving parts: a std::queue<std::function<void()>> guarded by a mutex; workers that wait on a condition variable with the predicate "stopping or queue not empty"; submit that pushes a task and returns a std::future (via std::packaged_task) so callers get the result or the exception; and a destructor that sets stopping, wakes everyone and joins. Workers drain the queue before exiting, so accepted work is never silently dropped.

Decide and state the policy: bounded or unbounded queue, what submit does when full (block, reject, run in the caller), and what happens to tasks queued at shutdown.

The smell

  • std::thread created inside a loop, one per request.
  • Tasks that never report completion or failure.
  • A detached thread that outlives the objects it captured.
  • A destructor that does not join, or a stop flag read without the mutex.

Before

#include <iostream>
#include <thread>
#include <vector>

// One thread per task: eight tasks, eight threads. Ten thousand tasks would mean ten thousand threads.
int main() {
    constexpr int kTasks = 8;
    std::vector<long long> results(kTasks, 0);
    {
        std::vector<std::jthread> threads;
        for (int i = 0; i < kTasks; ++i) {
            threads.emplace_back([&results, i] { results[i] = static_cast<long long>(i + 1) * (i + 1); });
        }
        std::cout << "threads created: " << threads.size() << "\n";
    }
    long long sum = 0;
    for (const long long r : results) sum += r;
    std::cout << "sum of squares: " << sum << "\n";
}

After

#include <condition_variable>
#include <cstddef>
#include <functional>
#include <future>
#include <iostream>
#include <memory>
#include <mutex>
#include <queue>
#include <thread>
#include <type_traits>
#include <utility>
#include <vector>

// A small fixed-size pool. Not copyable or movable: workers hold 'this'.
class ThreadPool {
public:
    explicit ThreadPool(std::size_t workers) {
        for (std::size_t i = 0; i < workers; ++i) workers_.emplace_back([this] { workLoop(); });
    }

    ~ThreadPool() {
        {
            std::lock_guard<std::mutex> guard(mutex_);
            stopping_ = true;
        }
        wake_.notify_all();
        // workers_ is declared last, so the jthreads join before the queue, mutex and condition variable are destroyed.
    }

    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;

    std::size_t size() const { return workers_.size(); }

    template <typename Task>
    std::future<std::invoke_result_t<Task>> submit(Task task) {
        using Result = std::invoke_result_t<Task>;
        auto packaged = std::make_shared<std::packaged_task<Result()>>(std::move(task));
        std::future<Result> future = packaged->get_future();
        {
            std::lock_guard<std::mutex> guard(mutex_);
            queue_.push([packaged] { (*packaged)(); });
        }
        wake_.notify_one();
        return future;
    }

private:
    void workLoop() {
        for (;;) {
            std::function<void()> job;
            {
                std::unique_lock<std::mutex> lock(mutex_);
                wake_.wait(lock, [this] { return stopping_ || !queue_.empty(); });
                if (queue_.empty()) return;  // stopping and drained
                job = std::move(queue_.front());
                queue_.pop();
            }
            job();  // run outside the lock
        }
    }

    std::mutex mutex_;
    std::condition_variable wake_;
    std::queue<std::function<void()>> queue_;
    bool stopping_ = false;
    std::vector<std::jthread> workers_;
};

int main() {
    constexpr int kTasks = 8;
    ThreadPool pool(3);
    std::vector<std::future<long long>> futures;
    for (int i = 1; i <= kTasks; ++i) {
        futures.push_back(pool.submit([i] { return static_cast<long long>(i) * i; }));
    }
    std::cout << "threads created: " << pool.size() << "\n";
    long long sum = 0;
    for (auto& f : futures) sum += f.get();
    std::cout << "sum of squares: " << sum << "\n";
}

What changed, and the trade-off

Three workers serve eight tasks (or eight thousand) with a constant thread count. submit returns a std::future, so the caller can wait for the value and any exception thrown by the task is rethrown at get(). The predicate-based wait covers spurious and lost wake-ups, jobs run outside the lock so a slow task never blocks submit, and shutdown is RAII: set the flag under the mutex, wake all workers, let them drain the queue, join.

Trade-offs: this queue is unbounded, so a fast producer can exhaust memory; a bounded queue adds a second condition ("not full") and a policy (block, reject or caller-runs). One shared queue is a contention point at high task rates (work-stealing queues per worker fix that, with more complexity). Tasks that block on other tasks in the same pool can starve it. submit after destruction began is a caller bug here; a production pool would reject it.

Say it in the interview

Draw the four parts (queue, mutex plus condition variable, workers, future) before coding, and state the shutdown policy. Senior signal: predicate wait, run-outside-the-lock, member declaration order for safe destruction, exceptions delivered through the future. Staff signal: bounded queues with back-pressure, work stealing, task priorities, and why you would normally use an existing executor rather than write one.

When it goes too far

A pool is not free either: sizing it wrongly (too few for blocking I/O, too many for CPU work) hurts, and one global pool shared by unrelated work lets a slow subsystem starve everyone. For one-off background work, std::async or a single dedicated thread is simpler. In real systems prefer a vetted executor library to a hand-rolled one.
