DRY, KISS, YAGNI, Demeter and tell-don't-ask

“Cheap rules that stop designs from rotting: one source of truth, no speculation, short dependency chains, behaviour next to data.”

These heuristics are weaker than the SOLID principles and often pull against each other, so treat them as prompts to think, not laws.

  • DRY: one source of truth for each piece of knowledge (not each piece of text).
  • KISS: the simplest design that meets today's requirements.
  • YAGNI: do not build for requirements you only imagine.
  • Law of Demeter: talk to your neighbours, not their neighbours: avoid a.getB().getC().doIt().
  • Tell, don't ask: tell an object what to do instead of pulling out its state and deciding for it.

The smell

  • order.getCustomer().getAddress().getCity() chains in callers.
  • Code that reads three getters and then applies a rule that belongs to that object.
  • The same business rule written in two places that must stay in step.
  • An abstract factory for something with one implementation.

Before

#include <iostream>

class Account {
public:
    explicit Account(int balance) : balance_(balance) {}
    int getBalance() const { return balance_; }
    void setBalance(int b) { balance_ = b; }
private:
    int balance_;
};

// Asks for state, decides outside, writes it back: the rule leaks into every caller.
bool withdraw(Account& a, int amount) {
    if (a.getBalance() >= amount) {
        a.setBalance(a.getBalance() - amount);
        return true;
    }
    return false;
}

int main() {
    Account a(100);
    std::cout << withdraw(a, 70) << withdraw(a, 70) << " " << a.getBalance() << "\n";
}

After

#include <iostream>

class Account {
public:
    explicit Account(int balance) : balance_(balance) {}
    // The rule lives with the data it protects.
    bool withdraw(int amount) {
        if (amount > balance_) return false;
        balance_ -= amount;
        return true;
    }
    int balance() const { return balance_; }
private:
    int balance_;
};

int main() {
    Account a(100);
    std::cout << a.withdraw(70) << a.withdraw(70) << " " << a.balance() << "\n";
}

What changed, and the trade-off

The overdraft rule exists once, inside Account, so no caller can forget it and the balance can no longer be set to an arbitrary value. This is tell-don't-ask and DRY at once: one source of truth for "can we withdraw".

Trade-off: keep plain data carriers (DTOs, config) as simple structs. Tell-don't-ask applies to objects with behaviour and invariants, not to every record.

Say it in the interview

Use these as one-line justifications while coding: "I'll keep the rule inside Account so there's one place to change" or "I'm not adding a factory yet, there's one implementation (YAGNI)". Contradicting yourself (an interface for everything, yet claiming YAGNI) is a common red flag.

When it goes too far

DRY applied to coincidental similarity couples unrelated features: two functions that look alike but change for different reasons should stay separate (a little duplication is cheaper than the wrong abstraction). Demeter applied mechanically creates piles of one-line forwarding methods; stop when a chain crosses a stable value type like std::string.
