Mutex: lock with RAII, never by hand

“Own the lock with a guard object so every exit path (early return, exception) releases it.”

A mutex protects an invariant, not a variable: "stock is never negative", "the map and its size agree". Every access to the data that invariant covers happens while holding the same mutex, and the lock is held for as short a critical section as the invariant allows.

Calling lock() and unlock() yourself is the C++ equivalent of malloc/free: correct only if every path remembers. RAII fixes it. Use std::lock_guard for plain scoped locking, std::unique_lock when you need to unlock early or hand the lock to a condition variable, and std::scoped_lock for several mutexes at once (next lessons).

Keep the mutex private, next to the data it guards, and expose operations ("take n") instead of "lock, then touch fields". Never call unknown code (a callback, a virtual function) while holding a lock: you cannot know what locks it takes.

The smell

  • mutex.lock() and mutex.unlock() written out by hand.
  • An early return, continue or throw between lock and unlock.
  • Public data members plus a public mutex: callers are trusted to lock.
  • Locking inside a loop body just to read a flag that never changes.

Before

#include <iostream>
#include <mutex>
#include <thread>

// Inventory with hand-written locking. The early return forgets to unlock, so the lock leaks.
class Inventory {
public:
    explicit Inventory(int stock) : stock_(stock) {}

    bool take(int n) {
        mutex_.lock();
        if (n > stock_) return false;  // BUG: still locked
        stock_ -= n;
        mutex_.unlock();
        return true;
    }

    // Asks "could another thread get the lock right now?" from a probe thread.
    bool lockIsFree() {
        bool free = false;
        std::thread probe([this, &free] {
            free = mutex_.try_lock();
            if (free) mutex_.unlock();
        });
        probe.join();
        return free;
    }

    void rescueForTest() { mutex_.unlock(); }

private:
    std::mutex mutex_;
    int stock_;
};

int main() {
    Inventory inventory(3);
    std::cout << "take 5: " << (inventory.take(5) ? "ok" : "refused") << "\n";
    std::cout << "lock free after refusal? " << (inventory.lockIsFree() ? "yes" : "no") << "\n";
    inventory.rescueForTest();
}

After

#include <iostream>
#include <mutex>
#include <thread>

// Same behaviour, but the guard releases the lock on every path.
class Inventory {
public:
    explicit Inventory(int stock) : stock_(stock) {}

    bool take(int n) {
        std::lock_guard<std::mutex> guard(mutex_);
        if (n > stock_) return false;
        stock_ -= n;
        return true;
    }

    int stock() const {
        std::lock_guard<std::mutex> guard(mutex_);
        return stock_;
    }

    // Asks "could another thread get the lock right now?" from a probe thread.
    bool lockIsFree() {
        bool free = false;
        std::thread probe([this, &free] {
            free = mutex_.try_lock();
            if (free) mutex_.unlock();
        });
        probe.join();
        return free;
    }

private:
    mutable std::mutex mutex_;
    int stock_;
};

int main() {
    Inventory inventory(3);
    std::cout << "take 5: " << (inventory.take(5) ? "ok" : "refused") << "\n";
    std::cout << "lock free after refusal? " << (inventory.lockIsFree() ? "yes" : "no") << "\n";
    std::cout << "take 2: " << (inventory.take(2) ? "ok" : "refused") << "\n";
    std::cout << "stock left: " << inventory.stock() << "\n";
}

What changed, and the trade-off

lock_guard ties the lock to the scope: the refusal path, the success path and any exception all release it. The mutex is mutable so a const reader such as stock() can lock it, which keeps const-correctness honest (a const method that is safe to call from many threads).

Trade-off: a guard held for a whole function can be too coarse. When the slow part (I/O, a callback) does not touch the invariant, narrow the scope with a block or switch to unique_lock and unlock early. Coarse locks are simple and usually right first; fine-grained locks buy throughput at the price of reasoning about more invariants.

Say it in the interview

Name the invariant the mutex guards, state that the guard is private, and show lock_guard unprompted. Senior signal: const methods lock a mutable mutex, no callbacks run under the lock, and you can say why a global lock is a fine v1. Staff signal: you discuss contention, lock scope versus invariant scope, and when to shard the lock.

When it goes too far

Locking everything "to be safe" serialises the program and invites deadlock. A lock around data only one thread ever touches is pure cost, and a lock around a single independent counter is often better as an atomic. Guards also do not make a multi-step operation atomic if you drop and retake the lock between the steps.
