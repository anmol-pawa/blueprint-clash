Facade: one simple door into a messy subsystem

“Provide a small, task-shaped interface over several collaborating classes so callers stop orchestrating them by hand.”

A Facade is a class with a few intention-revealing methods that coordinate a subsystem. Instead of every caller creating a lexer, a parser and an emitter and calling them in the right order with the right checks, one Translator::translate(text) does it.

It reduces coupling (callers depend on one class), centralises the call sequence (so it changes in one place) and gives you a natural seam to fake in tests. It does not hide the subsystem: power users can still reach the parts when they need to. That is the difference from an encapsulation boundary you enforce with the module system.

Facade differs from Adapter in intent (simplify many classes versus translate one interface), and from a Mediator (a Facade is one-way: the subsystem does not know about it).

The smell

  • The same three-step call sequence copied into several callers.
  • Callers know the subsystem's internal order, invariants and error handling.
  • A change inside the subsystem breaks many unrelated files.
  • Onboarding docs say "first call A, then B, then check C".

Before

#include <iostream>
#include <sstream>
#include <string>
#include <vector>

class Lexer {
public:
    std::vector<std::string> tokenize(const std::string& source) const {
        std::vector<std::string> tokens;
        std::istringstream in(source);
        std::string word;
        while (in >> word) tokens.push_back(word);
        return tokens;
    }
};

class Parser {
public:
    bool valid(const std::vector<std::string>& tokens) const { return !tokens.empty(); }
};

class Emitter {
public:
    std::string emit(const std::vector<std::string>& tokens) const {
        std::string out;
        for (std::size_t i = 0; i < tokens.size(); ++i) {
            if (i > 0) out += ",";
            out += tokens[i];
        }
        return out;
    }
};

int main() {
    // Every caller has to know the order, the validity check and the error text.
    const Lexer lexer;
    const Parser parser;
    const Emitter emitter;
    for (const std::string source : {"a b c", ""}) {
        const auto tokens = lexer.tokenize(source);
        if (!parser.valid(tokens)) {
            std::cout << "error: empty input\n";
        } else {
            std::cout << emitter.emit(tokens) << "\n";
        }
    }
}

After

#include <iostream>
#include <sstream>
#include <string>
#include <vector>

// Subsystem classes, unchanged.
class Lexer {
public:
    std::vector<std::string> tokenize(const std::string& source) const {
        std::vector<std::string> tokens;
        std::istringstream in(source);
        std::string word;
        while (in >> word) tokens.push_back(word);
        return tokens;
    }
};

class Parser {
public:
    bool valid(const std::vector<std::string>& tokens) const { return !tokens.empty(); }
};

class Emitter {
public:
    std::string emit(const std::vector<std::string>& tokens) const {
        std::string out;
        for (std::size_t i = 0; i < tokens.size(); ++i) {
            if (i > 0) out += ",";
            out += tokens[i];
        }
        return out;
    }
};

// Facade: the one call most callers need. It owns the sequence and the error text.
class Translator {
public:
    std::string translate(const std::string& source) const {
        const auto tokens = lexer_.tokenize(source);
        if (!parser_.valid(tokens)) return "error: empty input";
        return emitter_.emit(tokens);
    }

private:
    Lexer lexer_;
    Parser parser_;
    Emitter emitter_;
};

int main() {
    const Translator translator;
    std::cout << translator.translate("a b c") << "\n";
    std::cout << translator.translate("") << "\n";
}

What changed, and the trade-off

The call sequence, the validity check and the error wording now exist once. Changing the subsystem (a new pass, a different order) edits Translator and nothing else. The subsystem classes are untouched and still usable directly by the rare caller that needs a single stage.

Trade-off: the Facade is a new thing to maintain, and it decides what the "simple" cases are. If it grows a method for every caller's need it turns into a god class, the opposite of what you wanted. Keep it task-shaped, keep logic in the subsystem, and let it accept its collaborators through the constructor if you want to fake them in tests.

Say it in the interview

Say "callers should depend on what they want done, not on how the parts are sequenced". Senior signal: you mention that a Facade must stay thin (it coordinates, it does not own business rules), that it makes a good test seam and a good place for cross-cutting concerns such as logging, and that you would not use one to paper over a subsystem that is itself badly designed.

When it goes too far

A Facade over two collaborators that one caller uses once adds nothing. A Facade that every layer must go through becomes a bottleneck of changes and a god class (see the Senior Review god-class rule). And a Facade that hides too much forces power users to bypass it, leaving two ways of doing everything. Add one when the same orchestration appears in at least two places.
