Each lesson: the smell, a C++ before and after, how to say it in an interview, and what over-applying it costs. Then drill it with cards.

  • L2 · Single Responsibility: one reason to change A class should answer to one actor: if two different teams can force edits to it, split it.
  • L2 · Open/Closed: extend without editing Add behaviour by adding code, not by reopening code that already works.
  • L2 · Liskov Substitution: honour the contract A subtype must keep every promise its base type makes, so callers never need to know which one they hold.
  • L2 · Interface Segregation: small, role-shaped interfaces No client should depend on methods it does not use; split fat interfaces by role.
  • L2 · Dependency Inversion: depend on abstractions you own High-level policy should not construct or know low-level details; both depend on an interface the policy owns.
  • L2 · DRY, KISS, YAGNI, Demeter and tell-don't-ask Cheap rules that stop designs from rotting: one source of truth, no speculation, short dependency chains, behaviour next to data.
  • L3 · Factory Method: let subclasses choose the product Write the algorithm against an interface and defer the choice of concrete class to an overridable creation method.
  • L3 · Abstract Factory: families that stay consistent Create whole families of related objects through one interface, so you can never mix families.
  • L3 · Builder: readable construction with validation Collect optional parameters step by step, validate once in build(), and hand back an immutable object.
  • L3 · Prototype: copy through the base pointer Give objects a virtual clone() so you can copy them without knowing their concrete type.
  • L3 · Singleton: one instance, and why to be careful Guarantee a single instance with a function-local static, but pass it in as a dependency instead of reaching for it.
  • L3 · Object Pool: reuse expensive objects Keep a fixed set of costly objects and lend them out, returning them automatically with RAII.
  • L3 · Dependency Injection: receive, do not construct A class should be given its collaborators (usually by constructor), not create them itself.
  • L4 · Adapter: make the old interface fit the new caller Wrap a class you cannot (or should not) change so it speaks the interface your code already depends on.
  • L4 · Bridge: two dimensions that vary independently Split an abstraction from its implementation so each can grow on its own, instead of one subclass per combination.
  • L4 · Composite: treat one and many the same way Give leaves and containers a common interface so recursive structures need no special cases at the call site.
  • L4 · Decorator: stack behaviour without a subclass per combination Wrap an object in another object with the same interface to add one behaviour, and stack wrappers in any order at run time.
  • L4 · Facade: one simple door into a messy subsystem Provide a small, task-shaped interface over several collaborating classes so callers stop orchestrating them by hand.
  • L4 · Flyweight: share the identical part When huge numbers of objects repeat the same read-only data, store that data once and point to it.
  • L4 · Proxy: a stand-in that controls access Put an object with the same interface in front of another to add laziness, caching, protection or remoting without the caller noticing.
  • L5 · Strategy: swap the rule, keep the caller Put each interchangeable rule behind one interface so the caller picks a policy instead of branching on a name.
  • L5 · Observer: publish a change without knowing who cares Let a subject notify a changing set of listeners through one interface, and hold them so a dead listener cannot dangle.
  • L5 · Command: turn an action into an object you can store and undo Wrap a request as an object with execute and undo so it can be queued, logged, repeated and reversed.
  • L5 · State: let the current mode decide what a call does Replace repeated switches on a mode flag with one object per state, each deciding its own behaviour and next state.
  • L5 · Template Method: fix the skeleton, vary the steps Let a base class own the order of the steps and let subclasses fill in only the steps that differ.
  • L5 · Iterator: walk a collection without exposing it Give clients a way to visit the elements in order without handing them the container's insides.
  • L5 · Chain of Responsibility: pass it along until someone owns it Link handlers in a line so each one either handles a request or passes it to the next, with an explicit answer at the end.
  • L5 · Mediator: one place where the colleagues meet Make peers talk to a coordinator instead of to each other, so the coupling is one-to-one instead of everyone-to-everyone.
  • L5 · Memento: save and restore state without breaking encapsulation Capture an object's state in an opaque token so it can be restored later, without exposing its internals.
  • L5 · Visitor: add operations without editing the classes Move an operation out of a class hierarchy into a visitor, so new operations do not touch the element classes.
  • L5 · Interpreter: a small grammar as a tree of objects Represent each rule of a tiny language as a class, so a sentence becomes a tree that evaluates itself.
  • L5 · Null Object: a do-nothing collaborator instead of null checks Replace an optional dependency's null checks with a real object whose methods deliberately do nothing.
  • L5 · Specification: name a business rule and combine it Turn a yes/no business rule into an object, so rules can be named, reused and combined with and, or, not.
  • L5 · Event-driven design: publish what happened, let others react Announce a fact as an event instead of calling every interested party, and choose between direct calls, a queue and a stored log.
  • L6 · Requirements to entities: nouns, verbs and CRC cards Underline the nouns and verbs in the brief, make the nouns classes, and give each verb to the class that already holds the data it needs.
  • L6 · Class diagrams: relationships as C++ ownership Composition means I own it, aggregation means I only point at it, dependency means I use it for one call. In C++ each one is a different member type.
  • L6 · State diagrams: events and states, not boolean flags If an object behaves differently over time, draw its states and events first, then make the code a closed set of states with one place that decides each transition.
  • L6 · Sequence diagrams: who calls whom, and what happens when a step fails A class diagram shows structure; a sequence diagram shows one scenario in time, and its failure branch is where the missing responsibility shows up.
  • L6 · Extension points: ask what will change, then put one seam there Read the requirements for words like 'later', 'each month' and 'per customer', and give only those places an interface; keep everything stable concrete.
  • L7 · Threads: share less, join, then combine The cheapest way to make threaded code correct is to give each thread its own data and combine the results after join.
  • L7 · Mutex: lock with RAII, never by hand Own the lock with a guard object so every exit path (early return, exception) releases it.
  • L7 · Condition variables: wait on a predicate, not a notification A notification is a hint to re-check the state; the state, under the mutex, is the truth.
  • L7 · Atomics: one atomic op is not an atomic decision Reading an atomic and then writing it is two steps; use one read-modify-write (compare-exchange or fetch_op) so the decision and the update cannot be split.
  • L7 · Deadlock: one global lock order, or lock them together Deadlock needs four things at once; remove circular wait by taking multiple locks in one agreed order, or all at once with std::scoped_lock.
  • L7 · Thread pool: fixed workers, a queue, and a clean shutdown Create a few workers once and feed them tasks through a mutex-guarded queue, instead of paying for a thread per task.
