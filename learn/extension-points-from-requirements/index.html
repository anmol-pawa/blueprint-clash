Extension points: ask what will change, then put one seam there

“Read the requirements for words like 'later', 'each month' and 'per customer', and give only those places an interface; keep everything stable concrete.”

Interviewers end many rounds with a change request: "now add a new kind of discount". The design that survives it has an abstraction exactly where the requirements hinted at variation, and nowhere else.

Run a short extension-point pass after the entities: for each rule or entity, ask "what is the evidence that this changes, and how often?" Evidence is in the wording: "promotions change every month" (extension point), "rounding is to whole cents" (stable). Then pay for a seam only at the first kind: an interface, with the stable parts left as plain classes and functions. The skill is choosing few seams and naming why each one exists.

The smell

  • Tier or type names compared as strings inside a calculation (if (tier == "gold")).
  • Adding a new variant means editing the class that also holds unrelated stable logic.
  • The opposite smell: an interface for every noun "in case", with one implementation each.

Before

#include <iostream>
#include <string>
#include <utility>

// Requirement: "promotions change every month". The discount rules are welded into the cart.
class Cart {
public:
    Cart(std::string tier, int cents) : tier_(std::move(tier)), cents_(cents) {}

    int total() const {
        int total = cents_;
        if (tier_ == "gold") {
            total -= total / 10;
        } else if (tier_ == "silver") {
            total -= total / 20;
        }
        return total;
    }

private:
    std::string tier_;
    int cents_;
};

int main() {
    std::cout << "gold " << Cart("gold", 1000).total() << "\n";
    std::cout << "silver " << Cart("silver", 1000).total() << "\n";
    std::cout << "basic " << Cart("basic", 1000).total() << "\n";
}

After

#include <iostream>
#include <memory>
#include <utility>

// The one seam: the requirement said discounts change, so only discounts are an interface.
class DiscountRule {
public:
    virtual ~DiscountRule() = default;
    virtual int apply(int cents) const = 0;
};

class NoDiscount : public DiscountRule {
public:
    int apply(int cents) const override { return cents; }
};

class PercentOff : public DiscountRule {
public:
    explicit PercentOff(int percent) : percent_(percent) {}
    int apply(int cents) const override { return cents - cents * percent_ / 100; }

private:
    int percent_;
};

class FlatOff : public DiscountRule {
public:
    explicit FlatOff(int cents) : cents_(cents) {}
    int apply(int cents) const override { return cents > cents_ ? cents - cents_ : 0; }

private:
    int cents_;
};

// Cart stays concrete: its arithmetic is stable, so it only depends on the seam.
class Cart {
public:
    Cart(int cents, std::unique_ptr<DiscountRule> rule) : cents_(cents), rule_(std::move(rule)) {}
    int total() const { return rule_->apply(cents_); }

private:
    int cents_;
    std::unique_ptr<DiscountRule> rule_;
};

int main() {
    std::cout << "gold " << Cart(1000, std::make_unique<PercentOff>(10)).total() << "\n";
    std::cout << "silver " << Cart(1000, std::make_unique<PercentOff>(5)).total() << "\n";
    std::cout << "basic " << Cart(1000, std::make_unique<NoDiscount>()).total() << "\n";
    // A new promotion is a new class; Cart is not edited.
    std::cout << "flat " << Cart(1000, std::make_unique<FlatOff>(200)).total() << "\n";
}

What changed, and the trade-off

The three existing lines are unchanged, so the refactor is behaviour-preserving, and the fourth line is a promotion the old Cart could only gain by editing its total(). Only the discount became an interface; Cart itself, money as integer cents and the arithmetic stayed concrete because nothing in the requirements said they vary. The cart owns its rule through unique_ptr (composition), which is also what the class diagram should show. Trade-off: a string tier like "gold" now has to be mapped to a rule somewhere (a small factory or a lookup table at the edge), which is the right place for that string.

Say it in the interview

Say the evidence aloud: "you said promotions change monthly, so discounts are my extension point; tax rounding is fixed, so I keep it concrete." Level signal: SDE II adds a seam when asked for the change; Senior predicts the seam from the wording before being asked; Staff also names what is deliberately closed and what the cost of the seam is (an indirection, a mapping at the edge).

When it goes too far

Putting an interface behind every noun "for flexibility" gives you a dozen one-implementation hierarchies, more files and indirection to read, and still not the right seam when the real change arrives. A seam is a bet on a specific axis of change; spread bets thinly and you pay for all of them.
