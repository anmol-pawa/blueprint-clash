# Blueprint Clash: Architecture

Record expensive-to-reverse decisions as ADRs in `docs/adr/NNNN-title.md`.

## 1. Stack
The same as Algo Clash: Next.js 16 (static export, `basePath` `/blueprint-clash`), React 19, TypeScript strict, PixiJS 8 (overworld, battles, Siege canvas), CodeMirror 6 (`@codemirror/lang-cpp`), Tailwind 4, IndexedDB saves with migrations and export/import, the Query Clash service worker (keep the worker-fragment fix), Vitest, native g++ verification and Playwright.

## 2. C++ toolchain and judge (shared with Algo Clash)
- **Reuse first.** If the reference clone `/home/user/algo-clash` already has a working in-browser C++ judge (`lib/judge/`, its ADR in `docs/adr/`), **copy it** (with attribution in a comment) rather than re-researching. Otherwise do the spike described in Algo Clash's ARCH §2.1: the primary candidate is `@yowasp/clang`, which ships libc++ for wasm32-wasip1. Record the numbers in an ADR here too.
- **Limits of the wasm sysroot (ADR 0001):** no C++ exceptions (build with `-fno-exceptions`; Workshop APIs use error returns) and no real threads (concurrency needs a cooperative scheduler shim or native-only cards; owner decision pending).
- **Multi-file projects:** the virtual filesystem holds `api.h` (read-only, provided), user files (`*.h`, `*.cpp`) and the hidden test driver. Compile all translation units and link. Diagnostics are mapped to file and line in the editor.
- **Test framework:** a tiny in-repo header `bp_test.h` (TEST macros, expectations, structured JSON output to stdout) used by behaviour tests natively and in the browser.
- **AST analysis for Senior Review:** run `clang++ -fsyntax-only -Xclang -ast-dump=json` (filtered to user files) in the compile worker. Parse it in TS (`lib/review/`) into a model (classes, bases, methods, virtual/override/const flags, fields and their access, function sizes, `new`/`delete` expressions, `dynamic_cast`, switch statements over enums).
  - Each rule is a pure function with positive and negative fixtures in tests.
  - If the JSON is too large or slow in the browser, fall back to `-ast-dump-filter` per class, or to a lightweight in-TS parse of declarations, and record an ADR.
- **OCP score:** a line diff (Myers) between snapshots, attributed to "pre-existing units" (classes and functions present before the storm) vs new units, using the AST model to map lines to units. Pure, tested.

## 3. Native verification (`npm run content:verify`)
For every Workshop problem:
- compile the reference with g++ and run all phase tests (base + each storm)
- check each `bad/*.cpp` design fails its documented storm or test
- run the Senior Review rules natively on reference and bad designs (the reference must have no blockers or majors)
- validate the responsibility rubric and the clarification menu (every storm requirement is revealable by at least one clarifying question)

**Package layout** (`content/workshop/<id>/`, types in `lib/workshop/types.ts`, loader `lib/workshop/load.ts`, structural checks `lib/workshop/validate.ts`, native phase runner `lib/workshop/verify.ts`):
`meta.ts` (requirements per phase, flagged hidden or not, plus documented bad designs), `brief.md`, `clarify.ts` (menu with essential/useful/noise questions and the requirements each reveals), `rubric.ts` (responsibilities and acceptable owner classes), `api.h`, `reference/`, `tests/{base,storm1..3}/` (cumulative: each phase re-runs earlier tests), `bad/<name>/`, `editorial.md` (required sections: Requirements, Reference design, Alternatives, Trade-offs, What breaks at 10x, Level signals) and `followups.ts` (at least 3, tagged by level). `npm run content:verify` runs `content/verify/*.verify.ts` through Vitest (`vitest.content.config.ts`). Senior Review on reference and bad designs arrives with B7.

For card content, predict-behaviour outputs are generated by compiling and running natively.

## 4. HLD simulator (`lib/sim/`), the heart of the Siege
**Model:** a tick-based fluid simulation (default tick = 1 simulated second) with analytic queueing latency, plus a discrete-event mini-simulator used to validate it at small rates.
- **Topology:** a typed graph of components (§GDD 5.6) with config, edges with network latency, and zones/regions.
- **Traffic:** sources with λ(t) (piecewise, diurnal, spikes), an operation mix (read/write/scan), a key popularity distribution (Zipf s over a keyspace) and payload sizes.
- **Per tick and component:** offered load → utilisation ρ = λ / (c·μ); latency from M/M/c (Erlang C) for ρ < 1; above ρ ≈ 0.95, queues grow (backlog carried across ticks), timeouts fire, and errors propagate according to retry policies (which feed amplified load back into the graph, so retry storms emerge naturally).
  - **Caches** compute their hit ratio from the key distribution, capacity and policy (LRU via the Che approximation, cross-checked by simulation) and TTL, and a flush triggers a stampede.
  - **DB replicas** carry replication lag (a distribution), and reads routed to replicas within the lag window count as stale.
  - **Leaderless stores** evaluate N/R/W against failed nodes.
  - **Sharded stores** map keys to shards via the chosen strategy, so hot keys create hot shards.
  - **Queues** absorb bursts with backlog, consumer throughput and DLQ.
  - **Circuit breakers** run a closed/open/half-open state machine.
  - **Autoscaling** reacts to the metric with a delay and warm-up.
- **Chaos scheduler:** events at times (crash, partition, latency injection, region outage, flush, deploy, spike).
- **Outputs per tick:** throughput, errors, latency percentiles (p50/p95/p99, from a per-tick mixture of component latency distributions along request paths), availability (against the SLO), stale reads, lost writes (async failover), cost, backlog.
- **Bottleneck analyser:** rules over the outputs that produce plain-language findings with links to lessons.
- **Validation tests (required before any Siege content):**
  - M/M/1 and M/M/c mean wait vs closed forms (±5 %)
  - Little's law on the DES
  - LRU hit ratio vs the Che approximation and vs simulation for Zipf(0.8–1.2)
  - quorum read-after-write logic on all N/R/W combinations up to N = 5
  - retry amplification vs the closed form for independent failures
  - consistent-hash placement and movement fractions on node add/remove vs expectation
  - determinism: same seed → identical results
- **Performance:** runs in a Web Worker. A 10-minute simulated wave with 20 components finishes in ≤ 2 s on desktop. The UI animates sampled request particles only; the maths is in the worker.
- **Costs:** illustrative unit prices per component-hour, in-game currency only, documented as illustrative (not real cloud pricing).

## 5. Concurrency explorer (`lib/concurrency/`)
- A small step-based IR for threads (`load`, `store`, `lock`, `unlock`, `wait`, `notify`, `cas`, `atomicAdd`…), with programs authored in TS alongside the C++ snippet shown to the player. A test checks the snippet and IR stay in sync via a shared source.
- A manual scheduler UI and a bounded exhaustive explorer (DFS over interleavings with state hashing) that reports invariant violations, deadlocks and lost wake-ups.

## 6. Estimation solvers (`lib/estimation/`)
Pure functions for QPS, storage, bandwidth, cache sizing, fleet and shard sizing, availability ↔ downtime, Bloom filter false-positive rate, and HyperLogLog error. Every Fermi Forge answer is derived from these, and tests pin worked examples.

## 7. Game runtime and routes
`game/` holds the Pixi scenes (city overworld, battles, the Siege). `lib/battle/`, `lib/srs/`, `lib/save/`, `lib/audio/` and `lib/dialogue/` mirror Algo Clash (port them if present).

Routes: `/` · `/play` · `/workshop/[id]` · `/siege/[id]` · `/interview` (system design mock) · `/mock/lld` · `/race` (Race Hunter) · `/forge-estimates` · `/library` · `/journal` · `/trainer` · `/settings` · `/dev/sprites` · `/dev/judge` · `/dev/sim` (simulator playground with charts).

## 8. Budgets
First-load JS ≤ 300 KB gzip (the toolchain and simulator worker are lazy), a 60 fps city overworld on an iPhone 14, a smooth Siege canvas at 30+ fps with 20 components on desktop, no console errors, and no horizontal overflow at 390 px.

## Save system (`lib/save/`)

One IndexedDB slot (`blueprint-clash-save`/`slot1`) holding a versioned `SaveData` (player, badges, lessons done, Workshop records, SRS cards, settings). `loadSave` migrates old versions through the ordered `MIGRATIONS` chain (each step `n -> n+1`, pure), validates the result, and on a missing, corrupt or newer-than-game save returns a fresh in-memory save plus a warning without overwriting the stored value, so the player can still export it. Export is a JSON envelope (`app`, `version`, `checksum` = FNV-1a over canonical JSON); import checks the envelope and checksum, migrates, then validates. Editor drafts live in their own store (`lib/editor/drafts.ts`) so large code never bloats the save.

## World and dialogue (`lib/world/`, `lib/dialogue/`)
Pure, DOM-free logic that the Pixi overworld (B2b) drives. A `MapDef` is a row-string tile map (the characters are the keys of the scene legend used by the art), a `solid` character set, NPCs, warps and readable signs. `step()` is one grid step: a new direction only turns, the facing direction moves; warp tiles (doors, mats) are checked before solidity. `facingTarget()` resolves the NPC or sign being faced. `validateMaps()` rejects ragged rows, unknown legend characters, NPCs on solid tiles and warps landing on blocked tiles. A `DialogueScript` is a node graph (`next` or `choices`, `set` flags, `requires` gating); `advance()` is pure and never mutates the caller's flags; `validateScript()` rejects dangling and unreachable nodes.

`game/overworld/OverworldGame.ts` is the Pixi scene driven by that logic (route `/play`): tiles from the tileset textures (animated tiles tick), a 0.2 s tile-to-tile tween, walker sprites with a depth sort by row, integer scale (3× wide, 2× phone) and a camera clamped to the map edges (maps smaller than the view are centred). Doors walk the player onto the warp tile, then swap maps. Dialogue UI, portraits, the D-pad and the A button are React/DOM on top (crisp text, 44 px+ targets); keyboard is arrows/WASD plus Enter/Space/Z.

## Card battles (`lib/battle/`, `content/cards/`)
Pure, seeded logic: `battle.ts` (`startBattle`, `answerCard`, `grade`, `drawDeck`, option shuffling with answer remap), `deck.ts` (`validateDeck`, `buildPredictCards`) and `types.ts` (mcq, multi, pattern, smell, predict). Correct = attack (+5 per consecutive hit, capped at +15), wrong = the foe's counter and the streak resets. Predict-behaviour answers are never typed: `content/cards/predict-sources.ts` holds programs and distractors, and `content/verify/cards.verify.ts` compiles each with g++ (ASan + UBSan), runs it and compares with `predict.generated.json` (regenerate with `GEN_PREDICT=1 npm run content:verify`). Card art/UI is the Pixi battle stage (B3b).
