Template Method: fix the skeleton, vary the steps

“Let a base class own the order of the steps and let subclasses fill in only the steps that differ.”

A Template Method is an algorithm whose outline never changes but whose steps do. The base class owns the outline in one public, non-virtual function (run()), and calls small virtual steps that subclasses override. The order, the setup and the clean-up live in exactly one place, so a subclass cannot forget the closing step or run the steps out of order.

In C++ the idiomatic form is the non-virtual interface (NVI): the public function is not virtual, and the steps are private or protected virtuals. A subclass can still override a private virtual; it just cannot call it, which keeps the contract narrow. Optional steps are hooks: virtual functions with a harmless default (usually empty) that a subclass may override.

Template Method uses inheritance to vary the steps. Strategy uses composition to vary a whole algorithm. If the steps need to change at runtime, or you would rather not tie the variants to a base class, pass the steps in (Strategy) instead.

The smell

  • Two or three functions or classes repeat the same sequence (open, work, close) and differ in the middle.
  • A fix to the sequence (a missing close, a new log line) has to be copied to every variant.
  • One variant has quietly drifted: it skips a step the others perform.
  • A comment says "remember to call this at the end".

Before

#include <iostream>

// Each exporter repeats the skeleton by hand. The text one forgot to close.
void exportCsv() {
    std::cout << "open\n";
    std::cout << "id,name\n";
    std::cout << "1,Ada\n";
    std::cout << "close\n";
}

void exportText() {
    std::cout << "open\n";
    std::cout << "ID NAME\n";
    std::cout << "1 Ada\n";
}

int main() {
    exportCsv();
    exportText();
}

After

#include <iostream>
#include <memory>

// The base class owns the order of the steps. Callers use run(); nobody can skip "close".
class Exporter {
public:
    virtual ~Exporter() = default;
    void run() const {
        std::cout << "open\n";
        writeHeader();
        writeRows();
        writeFooter();
        std::cout << "close\n";
    }

private:
    virtual void writeHeader() const = 0;
    virtual void writeRows() const = 0;
    virtual void writeFooter() const {}  // hook: optional, empty by default
};

class CsvExporter : public Exporter {
private:
    void writeHeader() const override { std::cout << "id,name\n"; }
    void writeRows() const override { std::cout << "1,Ada\n"; }
};

class TextExporter : public Exporter {
private:
    void writeHeader() const override { std::cout << "ID NAME\n"; }
    void writeRows() const override { std::cout << "1 Ada\n"; }
    void writeFooter() const override { std::cout << "-- end\n"; }
};

int main() {
    std::unique_ptr<Exporter> csv = std::make_unique<CsvExporter>();
    std::unique_ptr<Exporter> text = std::make_unique<TextExporter>();
    csv->run();
    text->run();
}

What changed, and the trade-off

The sequence now exists once. The text exporter's missing close was a copy-and-paste drift; with the skeleton in the base class that bug cannot be written. writeHeader and writeRows are pure virtual (every variant must supply them) while writeFooter is a hook with a default. Because run() is non-virtual, no subclass can change the order, and because the steps are private, callers cannot call them in a different order either.

Trade-offs: the variants are welded to the base class, and a deep chain of overrides is hard to follow. Adding a step to the skeleton changes every subclass's behaviour at once, which is the point and also the risk. A virtual call from a constructor or destructor does not reach the derived override, so never run the template from a base-class constructor. When variants need to be picked or swapped at runtime, or are better as small values, prefer Strategy (compose the steps in).

Say it in the interview

Say "the order is invariant and only these steps vary". Show run() non-virtual and the steps private virtual, and name the hooks. Senior signal: you mention NVI and why (one place to add logging, locking or pre/post-conditions), the constructor-virtual-call trap, and the contrast with Strategy (inheritance versus composition). It appears in real problems as the processing pipeline of a game turn, a report generator, or a payment flow with validate, authorise, capture.

When it goes too far

A hierarchy to share two lines of code is not worth the coupling. If subclasses override most of the steps, or override the skeleton itself, the base class is not buying you anything. Many hooks make a framework nobody can reason about: a subclass has to know which hooks interact. And do not use inheritance for reuse when a free function or a Strategy would do.
