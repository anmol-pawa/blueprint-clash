Null Object: a do-nothing collaborator instead of null checks

“Replace an optional dependency's null checks with a real object whose methods deliberately do nothing.”

A Null Object is a real implementation of an interface that does nothing on purpose. Instead of passing nullptr for "no logger" and checking if (logger) at every use, you pass a NullLogger. The caller treats it like any other Logger; the conditional disappears, and so does the class of bugs where one check was forgotten.

In C++ two things make it stronger: own the collaborator with std::unique_ptr (or take a reference) and normalise in the constructor, so the member can never be null. Then the rest of the class is written as if the collaborator always exists.

The pattern is only right when "do nothing" is a correct answer. A logger, a metrics sink, an audit hook and a default-empty discount strategy qualify. A payment gateway does not: silently doing nothing there turns a missing dependency into lost money.

The smell

  • if (ptr != nullptr) before almost every call on one dependency.
  • A bug report that is a crash in the one method where someone forgot the check.
  • Tests that pass nullptr to avoid constructing a real collaborator.
  • A comment: "may be null".

Before

#include <iostream>
#include <string>

class Logger {
public:
    virtual ~Logger() = default;
    virtual void log(const std::string& line) = 0;
};

class ConsoleLogger final : public Logger {
public:
    void log(const std::string& line) override { std::cout << "log: " << line << "\n"; }
};

// The logger is optional, so every use needs its own null check. One forgotten check is a crash.
class Service {
public:
    explicit Service(Logger* logger) : logger_(logger) {}
    void charge(int amount) {
        if (logger_ != nullptr) logger_->log("charging " + std::to_string(amount));
        std::cout << "paid " << amount << "\n";
        if (logger_ != nullptr) logger_->log("done");
    }

private:
    Logger* logger_;
};

int main() {
    ConsoleLogger console;
    Service quiet(nullptr);
    Service chatty(&console);
    quiet.charge(5);
    chatty.charge(7);
}

After

#include <iostream>
#include <memory>
#include <string>
#include <utility>

class Logger {
public:
    virtual ~Logger() = default;
    virtual void log(const std::string& line) = 0;
};

class ConsoleLogger final : public Logger {
public:
    void log(const std::string& line) override { std::cout << "log: " << line << "\n"; }
};

// Does nothing, on purpose. It is a real Logger, so callers never ask "is there one?".
class NullLogger final : public Logger {
public:
    void log(const std::string&) override {}
};

class Service {
public:
    explicit Service(std::unique_ptr<Logger> logger = nullptr)
        : logger_(logger ? std::move(logger) : std::make_unique<NullLogger>()) {}
    void charge(int amount) {
        logger_->log("charging " + std::to_string(amount));
        std::cout << "paid " << amount << "\n";
        logger_->log("done");
    }

private:
    std::unique_ptr<Logger> logger_;  // never null: the constructor guarantees it
};

int main() {
    Service quiet;
    Service chatty(std::make_unique<ConsoleLogger>());
    quiet.charge(5);
    chatty.charge(7);
}

What changed, and the trade-off

Service no longer branches. Its constructor accepts a std::unique_ptr<Logger> and swaps a nullptr for a NullLogger, so logger_ is never null and every call site is one line. The output is identical in both versions; what changed is that a forgotten check can no longer exist. NullLogger is final and has no state, so it is also a good test double.

Trade-offs: a Null Object can hide a real configuration mistake: if production should always have a real logger, a silent default means you find out during an incident. Make "no-op by choice" explicit (the caller asks for NullLogger) when absence is a bug, or fail fast instead. For genuinely optional values (not collaborators), std::optional makes absence visible in the type and is usually better. A Null Object also needs sensible return values for non-void methods ("zero discount", "empty list"), which must be the neutral element of the operation.

Say it in the interview

Mention it when you see repeated null checks on a collaborator. Say "the default is a real object that does nothing", normalise it in the constructor, and keep the member non-null. Senior signal: you separate "absence is fine" (logger, metrics) from "absence is an error" (payments, auth), and name std::optional and fail-fast as the alternatives. It is a natural fit for a "no discount", "no notification" or "no-op cache" default in machine-coding problems.

When it goes too far

Using a Null Object to paper over a dependency that must exist swallows errors. Creating a Null variant of every interface adds classes nobody needed, and null objects with non-neutral return values ("zero" for a price that should be an error) corrupt results quietly. If there is exactly one call site, one if is clearer than a new class.
