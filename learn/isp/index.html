Interface Segregation: small, role-shaped interfaces

“No client should depend on methods it does not use; split fat interfaces by role.”

A fat interface couples every implementer and every client to the union of all roles. Implementers are forced to write stubs; clients get a recompile whenever an unrelated method changes.

Segregate by client need: the code that reads a document wants Readable; the code that saves one wants Writable. A concrete class may implement several small interfaces.

The smell

  • Overrides that are empty, return a dummy value, or throw unsupported.
  • A mock in tests with twenty methods when the test uses two.
  • A change to one method forces unrelated implementers to recompile.

Before

#include <iostream>
#include <stdexcept>

class Storage {
public:
    virtual ~Storage() = default;
    virtual int read() const = 0;
    virtual void write(int v) = 0;
    virtual void erase() = 0;
};

// A read-only snapshot is forced to fake the mutators.
class Snapshot : public Storage {
public:
    explicit Snapshot(int v) : v_(v) {}
    int read() const override { return v_; }
    void write(int) override { throw std::logic_error("read-only"); }
    void erase() override { throw std::logic_error("read-only"); }
private:
    int v_;
};

int show(const Storage& s) { return s.read(); }

int main() {
    Snapshot s(7);
    std::cout << show(s) << "\n";
}

After

#include <iostream>

class Reader {
public:
    virtual ~Reader() = default;
    virtual int read() const = 0;
};

class Writer {
public:
    virtual ~Writer() = default;
    virtual void write(int v) = 0;
};

class Snapshot : public Reader {
public:
    explicit Snapshot(int v) : v_(v) {}
    int read() const override { return v_; }
private:
    int v_;
};

class Cell : public Reader, public Writer {
public:
    int read() const override { return v_; }
    void write(int v) override { v_ = v; }
private:
    int v_ = 0;
};

// Depends only on the role it needs.
int show(const Reader& r) { return r.read(); }

int main() {
    Snapshot snap(7);
    Cell cell;
    cell.write(9);
    std::cout << show(snap) << " " << show(cell) << "\n";
}

What changed, and the trade-off

Snapshot no longer promises mutation it cannot deliver, so the "throws at runtime" trap is a compile error instead. Cell implements both roles through multiple inheritance of pure interfaces, which is safe in C++ because neither base carries state.

Trade-off: more names to learn, and a function needing both roles takes two parameters or a combined interface. Combine roles only where a real client needs them together.

Say it in the interview

Frame it by the client: "the checkout code only needs to charge, so it takes a Charger". Interviewers listen for roles named after what callers need, and for test doubles that stay tiny as a result.

When it goes too far

One interface per method (a "role" with a single function) fragments the design and pushes assembly work onto every caller. If every client uses the same three methods together, one interface with three methods is the right granularity.
