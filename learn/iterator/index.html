Iterator: walk a collection without exposing it

“Give clients a way to visit the elements in order without handing them the container's insides.”

An Iterator is a position plus a way to advance it, so a client can visit every element without knowing how they are stored. In C++ the pattern is built into the language: the standard containers hand out iterators, begin() and end() make a type usable in a range-based for, and the standard algorithms accept any iterator pair.

The design question is what you expose. Returning a reference to the internal std::vector lets callers add, remove and reorder elements behind your back, and welds every call site to vector. Exposing only begin() const and end() const gives read-only traversal, keeps your invariants, and lets you change the storage later without touching callers.

For your own structures (a tree, a ring buffer, a filtered view) you write a small iterator class: operator*, operator++, and operator!= (or ==), and the matching begin()/end(). State the invalidation rules: which operations on the container make outstanding iterators unsafe.

The smell

  • A getter returns a mutable reference to an internal container.
  • Callers index with for (i = 0; i < size(); ++i), so every caller knows it is random-access.
  • A "read" helper pops, sorts or erases the data it was meant to look at.
  • Changing the storage (vector to list) means editing every loop.

Before

#include <iostream>
#include <string>
#include <vector>

class Playlist {
public:
    void add(const std::string& title) { tracks_.push_back(title); }
    // Hands out the raw container: anyone can mutate it, and callers depend on std::vector.
    std::vector<std::string>& tracks() { return tracks_; }

private:
    std::vector<std::string> tracks_;
};

// A "print" helper that consumes the list it was only meant to read.
void printAll(Playlist& playlist) {
    auto& tracks = playlist.tracks();
    while (!tracks.empty()) {
        std::cout << tracks.front() << "\n";
        tracks.erase(tracks.begin());
    }
}

int main() {
    Playlist playlist;
    playlist.add("Dawn");
    playlist.add("Harbour");
    printAll(playlist);
    std::cout << "left: " << playlist.tracks().size() << "\n";
}

After

#include <iostream>
#include <string>
#include <vector>

class Playlist {
public:
    using const_iterator = std::vector<std::string>::const_iterator;

    void add(const std::string& title) { tracks_.push_back(title); }
    std::size_t size() const { return tracks_.size(); }

    // Read-only traversal. The storage type is an implementation detail behind these two functions.
    const_iterator begin() const { return tracks_.begin(); }
    const_iterator end() const { return tracks_.end(); }

private:
    std::vector<std::string> tracks_;
};

void printAll(const Playlist& playlist) {
    for (const auto& title : playlist) std::cout << title << "\n";
}

int main() {
    Playlist playlist;
    playlist.add("Dawn");
    playlist.add("Harbour");
    printAll(playlist);
    std::cout << "left: " << playlist.size() << "\n";
}

What changed, and the trade-off

printAll now takes a const Playlist&, so the compiler guarantees it cannot consume the list, and the range-based for works because the class has begin() and end(). Callers never mention std::vector: switching to a std::deque or a chunked structure changes one using line and two functions. The class keeps its invariants because mutation goes only through add.

Trade-offs: aliasing the standard iterator is the cheapest honest answer. For a structure that is not a flat sequence (a tree, a graph walk, a filtered view) you write an iterator class yourself, and you must document invalidation: adding to a vector can invalidate every outstanding iterator, while inserting into a std::list does not. A pair of iterators is also a poor fit for lazy or infinite sequences; a generator-style or range-based API suits those better. Never let an iterator outlive the container.

Say it in the interview

Say "clients should be able to traverse this, not mutate it or learn its layout". Offer begin() const and end() const, mention range-for and that the standard algorithms then work for free. Senior signal: you state iterator invalidation rules, know the category (forward, bidirectional, random-access) your own iterator should claim, and choose between exposing iterators, a visitor-style forEach callback, or a snapshot copy when the container is concurrent.

When it goes too far

Do not write a custom iterator class for a plain vector wrapper; an alias is enough. Do not build a full bidirectional random-access iterator when clients only need to visit once, a forEach(callback) is simpler. And exposing iterators from a class whose internals must stay private can leak more than a small accessor would, for example the ability to modify elements through a non-const iterator.
